# Campaign Config: Feed Providers, Channels, Presets, Country Groups, Articles

- **Feed Providers (v3):** Full sell-side provider management. `FeedProvider` type lives in `src/types/feed-provider.ts` (not `article.ts`). Key fields:
  - **Per-traffic-source config:** `urlConfig` ({baseUrl, parameters[]}) and `channelConfig` ({type, channelParamKey?}) now live INSIDE `snapConfig` and `metaConfig` (each source has its own). Top-level `FeedProvider.urlConfig`/`channelConfig` are DEPRECATED optional fields kept for back-compat reads; `upcast()` migrates legacy top-level values into `snapConfig`. `buildUrlTemplate(provider, article, headline, rac, adAccountId, trafficSource)` reads the launching source's urlConfig (fallback to top-level) and matches `article.domain` only among `domains` tagged for that source.
  - `snapConfig` — `organizationId?` (legacy, no UI), `allowedAdAccountIds[]`, `allowedPixelIds[]`, `campaignNamingTemplate?`, `revenueSource?: "visymo" | "predicto"` (pill in Snap tab; used by `getProviderNetworkMap()` to route source-coupled cron windows :15 vs :46), `urlConfig?`, `channelConfig?`
  - `metaConfig` — `allowedAdAccountIds[]`, `allowedPixelIds[]` (Meta pixels), `allowedPageIds[]` (**each page belongs to exactly one provider**, single-select in Traffic Sources), `pageId?` (legacy = `allowedPageIds[0]`), `campaignNamingTemplate?`, `revenueSource?: "predicto_fb" | "visymo"` (pill in Facebook tab — informational; Meta syncs every cron run), `urlConfig?`, `channelConfig?`. **Meta-traffic revenue sources:** Predicto FB (`predicto_fb_report`, joined by channel_id like Predicto→Snap) and Visymo (`visymo_report`, joined **directly** `custom_channel_name = meta_ad_set_id`, mirroring the Snap join `custom_channel_name = ad_squad_id`; EUR→USD). Both are LEFT-JOINed unconditionally in the combined metaQuery and summed into `revenue_usd` (only one is non-zero per ad set). Visymo already reports both Snap AND Facebook traffic in one feed — no separate token/table. At Meta launch, `pickBestPage()` selects the assigned page with the most ads remaining (running counts via POST /api/meta/page-ad-counts, scoped to the batch's allowed pages + allowedAdAccountIds), falling back to `pageId`/`allowedPageIds[0]`
  - `domains` — one shared `FeedProviderDomain[]` list; each domain's `trafficSources[]` ("Snap"/"Meta") controls which source tabs show it and which platform's URL builder may use it (a domain can be shared across both)
  - `urlConfig` — `parameters: UrlParameter[]` (key/value/encode with macro support). `UrlParameter.encode?: boolean` — when true, `encodeURIComponent` is applied to the fully resolved value in `buildUrlTemplate()`; old records without the field default to `undefined` (falsy, no change). `baseUrl` is retained in the stored shape as a backward-compat fallback but is no longer shown in the UI — base URLs are now per-domain.
  - `channelConfig` — `type: "provider-supplied" | "parameter-based"`, `channelParamKey?`
  - `domains[]` — `FeedProviderDomain` (`id`, `baseDomain`, `baseUrl?`, `trafficSources[]`). Each domain carries its own `baseUrl`. `buildUrlTemplate()` resolves base URL as `domain.baseUrl ?? provider.urlConfig.baseUrl ?? ""` (latter is the fallback for old records).

  **Modal tabs:** **Snap | Facebook** (2 traffic-source tabs only — Channels and Domains are no longer standalone tabs; there is no Combos tab). Each tab is a scrollable stack of sections for that source: Revenue Source, Assigned Ad Accounts, Allowed Pixels, URL Parameters (+ preview, via `UrlParametersTab` with `hideBaseUrl` + `platform`), Campaign Naming Template (shared `NamingTemplateEditor` — violet for Snap, blue for Meta; macros `{{preset.tag}}`, `{{article.name}}`, `{{date_ddmm}}`, `{{unique_id_4}}`, `{{creative.vname}}`, `{{channel.id}}`), Channels (`ChannelsTab` scoped to the tab's `trafficSource`), and Domains (`DomainsTab` filtered to the tab's source). The Facebook tab additionally shows Associated Facebook Pages (names resolved via `/api/meta/ad-limits`). URL/channel config are per-source (`snapConfig`/`metaConfig`); domains are one shared list tagged per source.

  **`UrlParametersTab` behaviour:** macro chips are always visible above the preview URL (not a focus-gated popup). Chips are filtered to only show macros not already present in any parameter value. Clicking a chip inserts into the last-focused value input (tracked via `lastActiveIndexRef`). Chips are split into two labeled groups: **Snapchat Native** (yellow — `{{campaign.id}}`, `{{adset.id}}`, `{{ad.id}}` — substituted by Snapchat at click time) and **BoilerRoom** (blue — all others — resolved before sending to Snapchat). Each parameter row has a compact **"enc" checkbox** (`accent-violet-500`); when checked it sets `UrlParameter.encode = true`, turns the label violet, and causes the preview URL to show the encoded value via `encodeURIComponent(p.value)`. Preview URL uses a structured renderer (not a flat split): base URL, parameter keys, `?`, `&`, and `=` are regular weight; hardcoded literal parameter values are **bold**; macros are highlighted yellow (Snapchat native) or blue (BoilerRoom). The `source` field on each MACROS entry (`"snap"` | `"br"`) drives both the chip style and the preview highlight color.

  Legacy records (only had `name`, `parameterName`, `baseUrl`) are up-cast by `upcast()` in `feed-providers.ts` — all new fields default to empty/sensible values. The board UI is a card grid; clicking a card or "New" opens `FeedProviderModal`. No separate `/new` or `/[id]/edit` route pages — everything is in the modal.

- **Feed provider channels:** Postgres table `feed_provider_channels` tracks channel lifecycle: `available → in-use → cooldown → available`. **Lifecycle is status-driven, not time-driven:** a channel stays `in-use` as long as the linked ad squad (Snap) or ad set (Meta) is effectively running. **The status poll must be routed by `traffic_source`** — `ad_squad_snap_id` holds a Snapchat squad UUID for Snap channels and a numeric Graph ad set id for Meta ones, so querying the wrong platform returns a 404 that the not-found branch reads as "entity deleted", stamping `paused_since` and releasing a channel whose campaign is still earning. For Snap, `paused_since` is stamped when `status = "PAUSED"`, `status = "DELETED"/"ARCHIVED"` or any non-ACTIVE status, `effective_status` present and not `"ACTIVE"` (e.g. all ads rejected), or the squad returns 404/"not found". For Meta the inactive set is explicit and narrower (`PAUSED`/`DELETED`/`ARCHIVED`/`CAMPAIGN_PAUSED`/`ADSET_PAUSED`/`DISAPPROVED`); transitional delivery states (`IN_PROCESS`, `PENDING_REVIEW`, `WITH_ISSUES`) count as live on purpose, since a false pause releases an earning channel while a false active only delays reuse. After 24h of continuous inactivity the channel moves to `cooldown`. If the squad is reactivated within 24h, `paused_since` is cleared. `cooldown → available` after 24h (unchanged). The cron job (`/api/reporting/cron-sync`, at :15 and :46 each hour per `vercel.json`) calls `syncChannelPausedStatus(googleUserId, { snapAccessToken, metaAccessToken })` (`src/lib/channel-status-sync.ts`) per user — two passes: (1) normal monitoring for channels with `ad_squad_snap_id`; (2) **backfill pass** for channels with `campaign_snap_id` but no `ad_squad_snap_id` (their fire-and-forget `link-squad` call failed) — lists the campaign's children on the owning platform (`getAdSquads` / `getAdSets`) and picks via `pickOwningAdSet()`, which requires a **unique ACTIVE** name match. A plain name match is not sufficient: `channel_id` is reused across relaunch variants, and it was ambiguous for 27 of the 28 orphans repaired on 2026-07-30. A wrong link is worse than none, because the exact-match arm of the reporting LATERAL join outranks the name fallback. The Meta token map is built before the Snap loop, and Meta-connected users with no Snapchat token get their own channel-sync pass — otherwise they never enter the loop at all. Lifecycle promotion transitions (`paused_since`-based and `cooldown_since`-based) are still lazy — `normalizeChannelStatuses(feedProviderId, googleUserId)` runs before every status-sensitive read. `releaseChannel()` (manual release) moves directly to `cooldown` regardless of squad status. **Bulk release:** `PATCH /api/feed-providers/channels` accepts `{ feedProviderId, newStatus }` (no `id`) to move all in-use channels for a provider in a single SQL UPDATE via `bulkForceChannelStatus()`. The Channels tab In Use section header shows **→ Avail All (N)** and **→ Cool All (N)** buttons when channels are present; per-row buttons are disabled while the bulk call is in flight. In Use rows with neither `campaign_snap_id` nor `ad_squad_snap_id` show an amber ⚠ badge ("Squad unknown — cannot auto-monitor"). `getAdSquad(adSquadId, token?)` accepts an optional token for cron use. DB functions: `getInUseChannelsByUser(googleUserId)`, `getInUseChannelsWithoutSquadId(googleUserId)` (filters `campaign_snap_id <> ''` as well as `IS NOT NULL` — both orchestrators assign with `campaignSnapId: ""` and only fill the real id in later via `link-squad`, and an empty string passes an `IS NOT NULL` test, producing a guaranteed-failing campaign lookup on every cron tick), `updateChannelPausedStatus()`, `bulkForceChannelStatus()`, `updateChannelAdSquadId()`. Channels are imported via CSV upload or manual textarea entry (one ID per line, optional `, TrafficSource` suffix) in the Channels tab. Both paths run a client-side deduplication pass against the already-loaded `channels` state before POSTing — existing IDs are silently stripped from the submission and reported in the status message (e.g. "Added 3. Skipped 2 already existing."); `INSERT ... ON CONFLICT (channel_id, feed_provider_id, google_user_id) DO NOTHING` in `bulkInsertChannels` is a DB-level backstop for the edge case where `channels` state is still `null`; the UNIQUE constraint `feed_provider_channels_unique_channel` makes the conflict target real — without it the ON CONFLICT clause was a no-op. `runMigrations()` adds the constraint idempotently via a TypeScript-level check against `pg_constraint` (deduplicate first, then `ALTER TABLE ... ADD CONSTRAINT`). The table has a `google_user_id` column — all queries filter by it to enforce per-user ownership.

- **Campaign presets (v3):** `CampaignPreset` key fields: `trafficSource?: "snap" | "facebook"` (defaults to `"snap"` on load for old records), `isCatalogue?: boolean` (Dynamic Collection Ads — hero Silo media + dynamic product tiles from the catalogue), `feedProviderId` (required; `""` for legacy), `tag?` (short label resolves `{{preset.tag}}` in naming templates), `creativeDefaults?: { adStatus }`. `brandName` field exists on the type but removed from `creativeDefaults` usage — no longer in UI. No `callToAction` — CTA is fixed per platform (`"MORE"` Snap, `"LEARN_MORE"` Meta), not configurable. Campaign is always saved as `status: "ACTIVE"`, `spendCapType: "NO_BUDGET"`, no start/end date. Ad squad always `spendCapType: "DAILY_BUDGET"`, no end date, no gender. `AdSquadPresetData` includes `catalogId?: string`, `productSetId?: string`, and `dynamicTemplateId?: string` for catalogue presets. `PresetForm` is a flat `max-w-2xl` form with a **Campaign Type** toggle at the top (Regular / Catalogue DPA), followed by Traffic Source + basic fields + targeting + bidding sections. When Catalogue is selected: violet config card shows Catalog ID (required) + Product Set ID (required) + Dynamic Template ID (optional). Pixel and Optimization Goal stay visible for BOTH types (Collection Ads use a pixel + PIXEL_PURCHASE like regular ads). `synthesizeCampaign` puts `catalogId` on the campaign and `productSetId`/`dynamicTemplateId` on the squad+creative. The targeting section has a **Smart placement** opt-in toggle (amber warning card) → sets `AdSquadPresetData.smartPlacement`; when true the launched squad is created with `placement_v2 { config: AUTOMATIC }` and becomes **read-only in-app** (E2025, manage in Ads Manager). This replaced the old dead `placementConfig` AUTOMATIC/CONTENT dropdown ("CONTENT" was rejected by the API with E39400). Default off = editable. Age targeting stored as strings (`"18"`, `"55"`) in `AdSquadPresetData.minAge`/`maxAge`; forwarded through `synthesizeCampaign()` into `AdSquadFormData`; merged into `targeting.demographics` alongside gender in `buildDemographics()` (`submission-orchestrator.ts`). Always exactly one ad squad. Old presets without `feedProviderId` show an amber "Provider not found" column label on the list page. `duplicatePreset(id)` in `lib/presets.ts` creates a copy named "Copy of X". The `/dashboard/presets` list is a board: one column per feed provider (`buildFeedColumns()` in `page.tsx`, sorted by preset count desc; presets with no/unknown `feedProviderId` get their own "No feed"/"Unknown feed" column), each column split into a Snap sub-group and a Facebook sub-group (colored pill-tag divider, not a dot) — when a provider has both, the column widens to `w-[560px]` and lays the two sub-groups out side by side in a `grid grid-cols-2`; a provider with only one traffic source stays a single `w-[300px]` column. Cards use full-width `StatRow`s (label + right-aligned bold value, hairline divider between rows) showing Pixel/Bid/Budget/Device for both platforms — Facebook cards additionally show a Geo group row above them, reading pixel via `metaPixelMap` (keyed by `SavedMetaPixel.pixelId`, loaded from `loadMetaPixels()`, since Meta and Snap pixels are separate stores) and formatting bid/budget via `metaBidText()`/`metaBudgetText()` (cents-based `MetaAdSetPresetData` fields, distinct from Snap's dollar-based `AdSquadPresetData` helpers) — with bordered Edit/Duplicate buttons + a borderless red Delete action; no "Load in Wizard" (preset selection happens in the wizard canvas).

- **Country Groups (live-linked geo-targeting):** `CampaignPreset.countryGroupId?: string` optionally links a preset to a named, reusable `CountryGroup` (`src/types/country-group.ts` — `{id, name, countryCodes, isWorldwide?, excludedCountryCodes?, createdAt}`; CRUD in `src/lib/country-groups.ts`, mirrors `pixels.ts`, KV key `br_country_groups`). **The link is live, not a one-time copy**: `geoCountryCodes` on `adSquads[0]`/`metaAdSet` still holds the last-resolved snapshot (display + fallback if the group is deleted), but `resolveGeoCountryCodes()`/`resolveMetaGeoTargeting()` in `synthesize-campaign.ts` re-read the group's *current* members at every campaign build (`synthesizeCampaign` calls the former for Snap; `synthesizeMetaCampaign` calls the latter, which additionally resolves `isWorldwide`/`excludedCountryCodes`) — editing a group changes every future campaign built from a linked preset, with no need to re-save the preset. This is safe because presets are only ever consulted at build time, never re-synced into an already-launched ad squad. **The snapshot must be read back on the no-linked-group path, not just written** — `resolveMetaGeoTargeting()` falls back to `metaAdSet.geoIsWorldwide`/`.geoExcludedCountryCodes` (not only `.geoCountryCodes`) whenever `countryGroupId` is absent or the group is gone. It previously hard-coded `isWorldwide: false` there, which made those two fields write-only: deleting a Worldwide group left every linked Meta preset with `geoCountryCodes: []` and no Worldwide flag, i.e. targeting nobody, even though `unlinkPresetsFromGroup()` had dutifully snapshotted the flag. `WORLDWIDE_AUTO_EXCLUDED_COUNTRIES` is applied to the snapshot path too (`withWorldwideExclusions()`), so an unlinked Worldwide preset keeps its TH/SG/TW exclusions. `PresetForm` shows a "Country Group" select above the Geo Targeting field; selecting a group resolves its countries (and Worldwide/exclusion flags) into a read-only display (**no per-preset override while linked** — unlink via "— Custom —" to edit manually). Managed from a "Country Groups" button next to "+ New Preset" on `/dashboard/presets`, opening `CountryGroupsModal` (list/create/edit/delete). Deleting a group that's linked to ≥1 presets warns with the usage count and calls `unlinkPresetsFromGroup()` (snapshots the group's current countries + Worldwide/exclusion flags into each linked preset, clears the link) before deleting. Country options live in `src/lib/countries.ts` (`COUNTRY_OPTIONS`, shared by `PresetForm` and `CountryGroupsModal`) — uses `"GB"` for the UK (not `"UK"`, which is not a valid ISO 3166-1 alpha-2 code and was previously a bug in the picker); `loadPresets()`/`loadCountryGroups()` backfill any stored `"UK"` to `"GB"` on load.
  - **Worldwide + Exclude Countries (added 2026-07-27, confirmed from a live manually-created ad set's raw JSON):** `CountryGroupsModal`'s form has a "🌍 Worldwide — target every country" checkbox (hides the Countries picker when checked, but **`countryCodes` is still saved** — targeting reads `isWorldwide`, not the list, so keeping it makes the toggle non-destructive; saving `[]` used to wipe the user's selection permanently, since re-opening the group for edit then showed an empty picker) and an always-visible "Exclude Countries" MultiSelect (`excludedCountryCodes`, independent of Worldwide). Save rejects a country present in both the target and exclude lists (non-Worldwide only) — overlapping lists otherwise hand Meta a self-contradicting spec to arbitrate silently. The list view shows "🌍 Worldwide" in place of the country list, plus an "excluding: …" line when exclusions are set. **Meta-only wiring**: `synthesizeMetaCampaign()`'s `resolveMetaGeoTargeting()` resolves the linked group's `isWorldwide`/`excludedCountryCodes` onto `MetaSynthesisResult.adSet.geoIsWorldwide`/`.geoExcludedCountryCodes` (also snapshotted onto `MetaAdSetPresetData` for display/fallback); `meta-submission-orchestrator.ts` then builds `targeting.geo_locations` as `{ country_groups: ["worldwide"] }` instead of `{ countries: [...] }` when `geoIsWorldwide` is true, and sets `targeting.excluded_geo_locations = { countries: [...] }` when the exclusion list is non-empty. **Exclusions are a sibling field, NOT a sub-field of `geo_locations`** — confirmed live 2026-07-27: an initial attempt at `geo_locations.excluded_countries` was rejected (error_subcode 1487079, "Normalization does not allow the value excluded_countries"); `MetaTargeting.excluded_geo_locations?: { countries?: string[] }` (`src/types/meta.ts`) is the real field, a top-level sibling of `geo_locations`. The `country_groups: ["worldwide"]` shape itself was confirmed live from a real Meta ad set targeting "WW" that was created manually in Ads Manager. **Snapchat is intentionally NOT wired up** — Snapchat's `targeting.geos` has no "worldwide" keyword or exclusion concept, so a Snap preset linked to a Worldwide/exclude-using group still resolves via the untouched `resolveGeoCountryCodes()`, which returns the group's raw `countryCodes` with no expansion or exclusion applied. **`PresetForm` now refuses to save a Snap preset linked to a Worldwide group** rather than relying on convention — it previously saved with an empty geo list and launched targeting nobody. `MetaTargeting.geo_locations` (`src/types/meta.ts`) is a **union** — `{ countries: string[]; country_groups?: string[] } | { countries?: string[]; country_groups: string[] }` — not two optional keys, so an empty `geo_locations` (no targeting at all) can't type-check its way into a Meta rejection; exclusions live on the separate `excluded_geo_locations` sibling field (see above). `PresetForm`'s `geoCountryCodes` Zod field dropped its `.min(1)` requirement (a Worldwide group legitimately has 0 countries) — the "select at least one country" check moved to a manual guard in `onSubmit` that's skipped only when the linked group is Worldwide **and** the preset is Meta. **First real Worldwide launch failed** (confirmed live 2026-07-27, error_subcode 3858498, "No Taiwan Universal Ads Declaration") because Worldwide necessarily reaches Taiwan/Singapore, which Meta requires a `regional_regulated_categories` declaration for — see that field's note under `meta-submission-orchestrator.ts` above. First fix attempt had the orchestrator auto-declare `regional_regulated_categories`; per a follow-up request this was replaced with **auto-exclusion instead**: `resolveMetaGeoTargeting()` merges `WORLDWIDE_AUTO_EXCLUDED_COUNTRIES = ["TH", "SG", "TW"]` (`src/lib/countries.ts`) into the resolved `excludedCountryCodes` whenever `isWorldwide` is true (in addition to whatever the group's own `excludedCountryCodes` already had), so Meta targeting simply never reaches these three countries — no declaration needed, and Thailand's separate age-restriction issue (see above) is sidestepped the same way. `CountryGroupsModal`'s form shows a note under the Worldwide checkbox when checked ("Worldwide will not target Thailand, Singapore, Taiwan due to Meta ad policy requirements") built from the same constant, so the two stay in sync if the excluded-country list ever changes.

- **Articles (v3):** `Article` type fields:
  - `slug` — "Keyword" in UI; plain string (no format restriction); resolves `{{article.name}}`
  - `query` — search keyword resolving `{{article.query}}`
  - `title?` — display title (optional, form only)
  - `previewUrl?` — URL for article preview; shown as a cyan "Preview" button in the table that opens a new tab
  - `domain?` — selected from the feed provider's `domains[]` (baseDomain); only domains belonging to the chosen provider are shown
  - `locale?` — locale code e.g. `"en_US"`; picked from a 10-option dropdown (German-Germany, English-AU/CA/GB/US, Spanish-AR/ES, Portuguese-Brazil, French-France, Italian-Italy)
  - `allowedHeadlines: { text: string; rac: string; metaHeadline: string; metaPrimaryText: string }[]` — each headline has a Snap text (≤34 chars), a RAC value, and its own Meta headline + Meta primary text (independent copy, used only for Meta ads). Old records (`string[]`, or missing the Meta fields) are migrated on load via `upcast()` (`rac`/`metaHeadline`/`metaPrimaryText` default to `""`). The **first entry in the list is always the default** — no stored index, no toggle. In the canvas wizard, the headline dropdown (`ArticleNode`) uses `h.text`; selecting a headline looks up that same entry's `rac`/`metaHeadline`/`metaPrimaryText` and stores all four on the canvas edge (`headlineRac`/`metaHeadline`/`metaPrimaryText` fields of `CampaignBuildItem`, threaded through `toggleProviderToArticle`/`setArticleContent` in `useCanvasStore.ts`). `rac` resolves `{{creative.rac}}` at synthesis time (Snap and Meta URLs alike); `metaHeadline`/`metaPrimaryText` are consumed only by `synthesizeMetaCampaign()` (falls back to the Snap `headline` text when empty, for articles that haven't set Meta copy) and populate the Meta ad creative's `name`/`title` (headline) vs `message` (primary text) — see the "Flexible ad format" note in docs/meta-api.md, which also documents that these two Meta fields used to wrongly share the same string. In the form (`ArticleForm.tsx`), each headline is stacked: text input on top, RAC input below in a muted gray style, then a bordered "Meta" sub-section (headline input + primary text textarea).
  - `trafficSources: string[]` — which platform(s) ("Snap"/"Meta") this article may be used with; mirrors `FeedProviderDomain.trafficSources` exactly (same field name and string values). Two checkboxes in `ArticleForm` ("Snap"/"Facebook" labels), at least one required. Legacy articles backfilled to `["Snap", "Meta"]` via `upcast()` in `lib/articles.ts` (non-breaking — preserves the previously-unrestricted behavior). Enforced in the canvas wizard: `CampaignCanvas`'s `isValidConnection` and `onConnect` block an article→account drag/connect when the target account's platform isn't in the article's `trafficSources` (checked alongside the existing `feedProviderIds` match).

  `FeedProvider` is imported from `src/types/feed-provider.ts` (not `article.ts`). The articles list page renders a sortable/filterable table (columns: Provider, Keyword, Language, Domain, Traffic, Headlines, Added, Actions). Provider colors use the same stable `PROVIDER_COLORS` palette as the canvas (providers sorted by `createdAt`, color by index) — consistent across both views. The Traffic column shows Snap/Meta pill badges (yellow/blue) per `article.trafficSources`. The Headlines column badge is clickable to expand a row showing all headlines and their RAC values. Action buttons are styled pills: gray Edit, cyan Preview (only when `previewUrl` set), red Delete.

  **`ArticleForm` gotcha:** `providers` loads async in a `useEffect`, so at mount the domain `<select>` has no options yet — the HTML select silently falls back to the first option. Fix: a second `useEffect` calls `setValue("domain", article.domain)` once `providers.length > 0`, restoring the saved value. Any future field that depends on a provider-driven option list should follow the same pattern.

  **`PresetForm` gotcha (same pattern):** `pixels` are loaded inside a `useEffect` — synchronous localStorage reads, but still deferred until after the first render. The Pixel `<select>` has no options on first render, so react-hook-form's `defaultValues.pixelId` silently falls back to "— None —". Fix: a restoration `useEffect` calls `setValue("pixelId", sq0.pixelId)` once `pixels.length > 0`. The hook must be placed *after* both `sq0` and `setValue` are declared (post-`useForm` destructuring) to avoid a temporal dead zone error.
