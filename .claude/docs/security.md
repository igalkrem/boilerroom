# Security Notes


- **CSRF: Origin is checked in the proxy. The matcher is now all non-asset paths, not just `/api/*`** (it widened for the CSP nonce — see the CSP entry), so this guard also covers page POSTs. `isCrossSiteWrite()` in `src/proxy.ts` rejects any non-GET/HEAD/OPTIONS request whose `Origin` header is present and does not match `x-forwarded-host` (nextUrl.host is an internal hostname behind Vercel's proxy). It deliberately does **not** reject a *missing* Origin — some clients omit it same-origin, and a cross-site browser POST always sends one. The matcher grew in two steps for this reason — from eight prefixes to all of `/api/*` (covering `/api/feed-providers/*`, `/api/presets/*`, which the old list missed), then to all non-asset paths for the CSP nonce. Rate-limit BUCKETS are unchanged; unmatched paths fall straight through the limiter but still get the Origin check. `/api/reporting/cron-sync` returns early, before both.
- **`getAppUrl()` (`src/lib/app-url.ts`) is the only way to build the app's own origin.** Six sites used `process.env.NEXT_PUBLIC_APP_URL || "http://localhost:3000"`; if that variable is ever missing in a production environment, every OAuth `redirect_uri` silently becomes localhost and a browser would carry the authorization code to whatever is listening on the user's own port 3000. It therefore **throws** in production rather than falling back, and gates on `NODE_ENV`, not on the variable being truthy. `NEXT_PUBLIC_APP_URL` is confirmed set for Development/Preview/Production on Vercel — if you add a new environment, set it there before deploying. `dev-login` deliberately does **not** use this helper.
- **Zod failures never echo `parsed.error.flatten()`.** `invalidRequest()` (`src/lib/api/validation-error.ts`) returns `{ error: "invalid_request", issues: ["path: message", …] }` and logs the full structure server-side. Applied at all 19 sites. Nothing on the client ever read the old `details` object.
- **`/api/meta/adsets` POST validates with typed fields + `.passthrough()`, NOT a closed `z.object`.** It was `z.record(z.string(), z.unknown())` — structurally unvalidated. A *closed* object here would silently strip `targeting`, `promoted_object`, `attribution_spec` and `regional_regulated_categories` and still return 200, which is the exact failure class this file warns about elsewhere. Budgets are pinned to positive **integers**: Graph truncates a fractional minor-unit value, turning a $10.50 intent into an unnoticed $10.00 cap. Validated against every stored preset before shipping.
- **SEC-21: `runMigrations()` tolerates concurrent DDL instead of locking. The `pg_advisory_lock` it used to take NEVER WORKED and was removed on 2026-08-05.** The `migrated` flag is per-instance, so a deploy waking N serverless instances runs the whole DDL block N times concurrently. `IF NOT EXISTS` is check-then-act inside Postgres and not atomic against a concurrent identical statement, so the losing instance errored and its request 500'd.
  - **Why the lock was inert:** measured live, immediately after `SELECT pg_advisory_lock(key)` on the app's own `sql` — **0** locks visible in `pg_locks`, `pg_try_advisory_lock` returned **true** instantly, `pg_advisory_unlock` returned **false**. The driver sends every query over Neon's HTTP endpoint, which does not preserve session state between statements, so a SESSION-level advisory lock is discarded the moment the statement returns. It was equally inert under `@vercel/postgres` (same HTTP path) — this was never protecting anything, for its entire life.
  - **Why tolerance beat fixing the lock:** a working lock needs the lock and the DDL on one pinned session (a WebSocket `Client`, not the HTTP callable), which adds a `ws` dependency on Node 20 and a new way for database init to fail, and makes the slowest cold start wait on every other instance. The DDL is already idempotent by construction (10 `CREATE TABLE IF NOT EXISTS`, 9 `ADD COLUMN IF NOT EXISTS`, 4 `CREATE INDEX IF NOT EXISTS`); the only defect was the error on the loser.
  - **`applyIdempotentDdl()` swallows exactly three measured SQLSTATEs** and rethrows everything else: `42P07` duplicate_table, `42701` duplicate_column, `42710` duplicate_object. **A duplicate CONSTRAINT reports `42P07`, not the `42710` you would expect**, because a UNIQUE constraint creates a backing index — confirmed by probe after assuming otherwise. `42P01` (undefined_table) and `42601` (syntax_error) are deliberately NOT tolerated: those are bugs in `migrations.sql`. **Never widen this to a bare `catch`** — and note a connection failure carries no SQLSTATE at all, so it correctly rethrows rather than marking migrations complete when nothing ran.
  - **Verified by forcing the race, not by reasoning:** 8 concurrent processes creating the same new table. Unguarded, 1 succeeded and **7 threw `42P07`** — reproducing the exact deploy failure. Guarded, **all 8 succeeded** with 7 logging the tolerated race. Test file `src/lib/db/concurrent-ddl.test.ts`; mutation-tested (bare catch fails 2, adding `42P01` fails 1).
  - The `kingsroad_report`→`visymo_report` RENAME branch is now **unreachable** — that table no longer exists — but is kept wrapped for environments restored from an older snapshot.
- **Token decryption is per-row, not one `.map()`.** `getAllUserSnapchatTokens`/`getAllUserMetaTokens` are called by the cron for *every* tenant; one row encrypted under a rotated `SESSION_SECRET` used to throw and abort the entire sweep, silently freezing all tenants' reporting. Bad rows are now logged and skipped.
- **CSP dropped `'wasm-unsafe-eval'` and `worker-src blob:`.** Both existed for the client-side ffmpeg.wasm transcoder; its only entry point (`transcodeVideoToH264` in `silo-utils.ts`) has **zero callers** — `/api/silo/transcode` does the work server-side with native ffmpeg — and `new Worker` appears nowhere in `src/`.
- **`script-src 'unsafe-inline'` is GONE, replaced by a per-request nonce (2026-08-03).** See the Content Security Policy entry further down in this file — the policy now lives in `src/proxy.ts`, **not** `next.config.mjs`.
- **Never save a session snapshot taken before `getValidAccessToken()`.** That helper takes its OWN `getSession()` and, on refresh, writes `snapAccessToken`/`snapRefreshToken`/`snapExpiresAt` and saves. Saving an older snapshot afterwards overwrites them, and because Snapchat **rotates** refresh tokens the cookie is then holding one Snapchat has already invalidated — the Snap connection fails for every later request until the user reconnects. This affected `upload-init`, `upload-finalize` AND `upload-from-blob`. Preferred fix is ORDERING: mutate and save the session *before* the token fetch so the token fetch is the last writer (`upload-finalize` does this). Where that is impossible because the value being stored comes from the upstream response (`upload-init` stores `upload_id`), re-read the session immediately before mutating — but note that this relies on a second `getSession()` observing a cookie written earlier in the same request, which is **unverified**; if token loss is ever seen there, the real fix is to have `getValidAccessToken()` return its session so callers mutate that instance. `upload-from-blob`'s 401/403 retry also had to re-read, because it was refreshing with the snapshot's already-rotated `snapRefreshToken` and so could never succeed.
- **`isOwnBlobUrl` fails CLOSED in production.** It used to return true for any `*.blob.vercel-storage.com` host when `BLOB_READ_WRITE_TOKEN` was missing — i.e. any Vercel customer's public store — and callers fetch that URL server-side and pass it to Snapchat/Meta as a `file_url`, making the fail-open SSRF-shaped. Writing to Blob requires the token anyway, so rejecting reads without it costs nothing; development keeps the permissive fallback. The missing-token warning is latched to once per process (it fired once per URL, and the catalogue delete path checks up to 50).
- **Token fetch goes AFTER validation and authorization on every route.** `media/upload` fetched it above both, so a caller about to be rejected still triggered a token fetch — and a refresh at that moment rotates the refresh token. `media/poll` was already correct.
- **`/api/reporting/combined` is not the only staleness path — see `healIfFeedsOverdue()`** in the performance page. Both mount and date-change now heal a range when any feed (visymo, predicto, **predicto_fb**) is more than 75 min stale. `handleDateChange` previously re-synced only when EVERY account returned zero rows, so a partially-populated range served from cache indefinitely. It keys on feed freshness rather than "any rows missing" on purpose: for a historical range the cache is as fresh as the cron made it, so syncing on every partial range would fire a sync on each date-shift click.
- **`MetaAd` deliberately does NOT extend `MetaAdPayload` wholesale.** Graph returns `creative: { id }` on reads while the create payload takes `creative: { creative_id }` — `creative_id` is write-only. Inheriting the payload shape made all three read sites cast the type away. `getAdSets()` also explicitly requests `bid_strategy` and `bid_constraints`: `MetaAdSet` declares them but Graph returns only what `fields=` names, and that omission is exactly what hid the ROAS bug.
- **Revenue in `/api/reporting/combined` is `visymo + predicto` on BOTH arms, guarded by `noteDualFeed()`.** The sum is only correct while an entity monetizes on exactly one feed (a provider uses one revenue source; a channel belongs to one provider). Measured 2026-07-30: the invariant holds everywhere — 0 overlaps across 4,726 Snap rows (949 visymo-only, 1,211 predicto-only) and 0 across 2,130 Meta rows (12 and 25). `noteDualFeed()` now checks it per row and logs `DUAL-FEED REVENUE` with the entity, date and both amounts if it ever breaks; grep for that string. It deliberately does **not** pick a leg — choosing the correct source needs to know which feed served the traffic, and guessing wrong would silently delete real revenue, a worse failure than a flagged overstatement. A dual-feed hit means a config error (e.g. an ad set id reused as a Visymo channel name while its channel is also mapped to Predicto), and that row's ROI and profit are inflated.
- **Do NOT add an upper bound to `bid_constraints.roas_average_floor`.** It looks like it needs one — two saved presets hold `roasFloor` 0.9 and 90, and the orchestrator sends `ratio * 10000`, so the second produces 900000 (a 90x return). But `roasDisplayDivisor` (per provider, Meta tab) is **not display-only**: it divides on read and multiplies back on save, and the Predicto provider has it set to **100**, so for that provider a cell reading "90%" legitimately stores 900000 and those ad sets deliver with real spend. No single ceiling is correct, because the right magnitude depends on which provider owns the ad set. A cap was written and reverted for exactly this reason — see the header comment in `src/lib/roas-floor.ts`.
- **`roas_average_floor` is `z.number().positive()` on both the create and PATCH paths.** PATCH previously took a bare `z.number()`, so zero and negatives passed — and PATCH is the live editor behind the performance table's ROAS cell, not a rarely-hit path. Positive-only is scale-independent and therefore safe; a ceiling is not.
- **Open decision — the ROAS scale convention is inconsistent.** Preset `roasFloor` is applied with **no** divisor (`meta-submission-orchestrator`), so a preset is implicitly bound to one provider's scale; that is why 0.9 and 90 both exist for what is the same intent. The note in `PerformanceTable` recommends the real fix: correct the stored floors at the source and set the divisor back to 1, rather than perpetuating the inflation on every save. That is a data migration, not a patch.
- **`getStoredAdAccountIds()` is display-only and must never gate access.** It returns the *persisted* ad account id lists. `report_sync_log` and the stats tables are keyed by the stored list (the cron iterates it) while the session carries the *live* `/me/adaccounts` list, and the two have been observed to drift (33 entries each, different contents). `/api/reporting/sync-status` unions them because every value derived is a MAX over timestamps. For authorization always use `isAdAccountAllowed` / `isMetaAdAccountAllowed` against the session alone.

- **Sign-in is restricted to one email domain:** `ALLOWED_EMAIL_DOMAIN = "adcore.com"` in `src/app/api/auth/google/callback/route.ts`. The check runs *before* any session field is written and also rejects `email_verified === false` (explicitly `=== false`, not falsy, so a missing claim cannot lock everyone out); rejected sign-ins redirect to `/login?error=not_authorized`. Previously **any** Google account became a fully provisioned tenant, which turned every per-tenant authorization gap into one reachable by anyone on the internet. To add someone outside the domain, extend this check — do not remove it.
- **Every `feed_provider_channels` read must filter `google_user_id`:** the eight LATERAL subqueries in `/api/reporting/combined` and `/api/reporting/drilldown` did not, so the attribution join read **every** tenant's channel rows (485 rows live at the time of the fix). That leaked other tenants' revenue into the dashboard *and* let a planted row displace a victim's own attribution, since the direct arm carries `_p = 0` and `ORDER BY _p LIMIT 1` makes it win. Both routes now derive `const userId = session.googleUserId ?? ""` and bind it into both arms. The network-classifier joins in `cron-sync` (threaded through `getAccountNetwork(..., googleUserId)`) and `sync-status` are scoped too.
- **ILIKE escaping uses `ESCAPE '!'`:** `REPLACE(REPLACE(REPLACE(channel_id, '!', '!!'), '%', '!%'), '_', '!_')` with an explicit `ESCAPE '!'` clause. The previous 2-level backslash version had no `ESCAPE` clause (relying on Postgres' default) and never escaped the backslash itself. `!` avoids backslash-escaping ambiguity between the JS template literal and the SQL string. Verified against live Postgres: `%` and `_` are literal, and the escape character itself round-trips.
- **`link-squad` verification is mandatory AND platform-aware:** it used to be wrapped in `if (isSnapchatConnected(session))`, so never connecting Snapchat (or disconnecting) skipped it entirely and allowed linking a channel to an arbitrary ad squad. Making it unconditional then broke every Meta launch, because the Meta orchestrator passes a **Meta ad set id** as `adSquadId` and Snapchat's `/adsquads/{id}` always 404s on it — and since both orchestrators fire this PATCH fire-and-forget, the link vanished silently. The route now branches on `platform`: Meta ids verify via `getAdSet()` + `isMetaAdAccountAllowed(act_<account_id>)`, Snap ids via `getAdSquad()` with a `getCampaign()` fallback for the optional `ad_account_id`. **Any new caller must send `platform`.** Both orchestrators now log a non-ok response instead of swallowing it. The Meta branch returns **401 `meta_token_expired`** rather than 422 when the token is unusable — Meta has no refresh (~60 d), so that is a routine state, and reporting it as a bad ad set id sends you hunting for an id the orchestrator just created.
- **Verifying a link-squad change without launching real ads:** mint an iron-session cookie locally with `sealData({ googleUserId, metaUserId, metaAccessToken, metaExpiresAt, metaAllowedAdAccountIds }, { password: SESSION_SECRET })` and PATCH the route on the dev server with a **nonexistent `channelId`** — the UPDATE then matches zero rows, so a 200 proves the verification gate cleared while nothing is written. Two gotchas that cost real debugging time: `metaExpiresAt` is **mandatory** (`getValidMetaToken()` gates on `Date.now() >= (metaExpiresAt ?? 0)`, so omitting it fails every call as `meta_token_expired`), and `user_meta_tokens.expires_at` is stored as **epoch-ms**, so `new Date(expires_at)` yields `NaN` — use `Number(expires_at)`. Also note `session.metaAllowedAdAccountIds` comes from a **live** `/me/adaccounts` call, not from `user_meta_tokens.ad_account_ids`; the stored column drifts from the live list, so never use it as a proxy when testing the allow-list gate.
- **Parent ids are verified on the Snap create paths:** `adAccountId` alone does not constrain `campaignId` (adsquads POST) or `adSquadId` (ads POST), so the allow-list check was decorative there. `adsquads` verifies the campaign; `ads` verifies the squad and — because `SnapAdSquad.ad_account_id` is optional in Snapchat's response — falls back to the squad's campaign (`SnapCampaign.ad_account_id` *is* required) rather than allowing the write through unverified. **These GETs are an extra abort point mid-launch, so classify their failures:** `isEntityNotFound(err)` (`src/lib/snapchat/errors.ts`) → `422 invalid_campaign_id`/`invalid_ad_squad_id`; anything else (429 after the limiter's retries, 5xx, timeout) → `503 verification_unavailable`. Collapsing both into 422 meant a transient blip aborted the launch — leaving a live campaign with zero ad squads, or a squad with zero ads — while blaming an id the orchestrator had itself created seconds earlier.
- **`mediaId` is shape-checked before path interpolation:** `SNAP_ID_RE = /^[A-Za-z0-9_-]{1,64}$/` / `isValidSnapId()` in `src/lib/snapchat/client.ts`, applied in `media/{upload,upload-from-blob,upload-init,poll}`. Deliberately permissive about the id *format* (pinning to 36 hex chars would break if Snapchat changes it) while excluding every character needed to escape a URL path segment.
- **Blob host pinning lives in one place:** `isOwnBlobUrl()` in `src/lib/blob-host.ts`, used by `/api/meta/media`, `/api/silo/transcode`, `/api/snapchat/media/upload-from-blob`, `/api/silo/delete`, `/api/catalogue/delete`. It parses the URL and requires the host to be **our** store, derived from `BLOB_READ_WRITE_TOKEN` (`vercel_blob_rw_<storeId>_<secret>`) — a plain `.endsWith(".vercel-storage.com")` matched *any* Vercel customer's public store. Falls back to the suffix-only check with a `console.warn` if the token is unparseable, so a misconfiguration degrades loudly instead of breaking every upload.
- **Client-upload tokens pin the pathname:** `onBeforeGenerateToken` in `/api/silo/upload` and `/api/catalogue/upload` validates the client-chosen `pathname` against `^silo/<uuid>/<safe-name>` / `^catalogue/<uuid>-<safe-name>`. Content type and size were already constrained but the path was not — a token could otherwise overwrite `metadata/{googleUserId}/*.json`, the trusted config store that `KVHydrationProvider` rehydrates from on every dashboard mount.
- **`verifyCronSecret` hashes before comparing:** both the received header and `Bearer ${CRON_SECRET}` are SHA-256'd, then compared with `timingSafeEqual`. `timingSafeEqual` *throws* on a length mismatch, and returning from that catch was observably faster than a full comparison — leaking the expected header length. Still fails closed when `CRON_SECRET` is unset.
- **`isAdAccountAllowed` denies by default:** When `session.allowedAdAccountIds` is empty (fresh session before dashboard loads), the function returns `false`. It is populated by `/api/snapchat/ad-accounts` — all Snapchat API routes that accept an `adAccountId` must call this check. Do NOT revert the default to `true`. The four Snapchat GET proxy routes (`campaigns`, `adsquads`, `creatives`, `ads`) require `?adAccountId=` and call `isAdAccountAllowed` before fetching. When a single entity ID is provided, each route also performs an IDOR ownership check — fetches the entity from Snapchat and asserts `entity.ad_account_id === adAccountId` — returning 403 if the entity belongs to a different account.
- **`/api/auth/dev-login` is the one route that mints a session without OAuth** — so it is gated twice and both gates must stay: `NODE_ENV === "production"` → 404 (so it cannot exist in a deployed build even if the secret leaked), and a missing/short/mismatched `DEV_LOGIN_SECRET` → 404 (compared with `timingSafeEqual`, never `===`). It deliberately does **not** accept an identity from the caller — a `?userId=` parameter would turn it into a log-in-as-anyone primitive — taking the user from `DEV_LOGIN_GOOGLE_USER_ID` or inferring it only when exactly one `user_snapchat_tokens` row exists. `?to=` is constrained to single-leading-slash relative paths so it cannot be used as an open redirect. Never set `DEV_LOGIN_SECRET` in Vercel env. Verified: 404 without/with wrong secret, 404 against the deployed origin, `//evil.example.com` falls back to `/dashboard`.

- **Meta API routes auth pattern:** All Meta routes (`/api/meta/campaigns`, `/api/meta/adsets`, `/api/meta/ads`, `/api/meta/creatives`, `/api/meta/media`, `/api/meta/pages`) check `isSessionValid()` → `isMetaConnected()` → `isMetaAdAccountAllowed()` (where applicable). Mutation endpoints perform IDOR protection: fetch entity from Meta, assert `account_id` matches. `/api/meta/media` validates `blobUrl` via `isOwnBlobUrl()` (`src/lib/blob-host.ts`) — it previously used a substring test on the whole URL (`url.includes(".vercel-storage.com")`), which `https://evil.tld/?x=.vercel-storage.com` defeated. Its **GET** half also requires an allowed `adAccountId` now: without it any signed-in caller could pass an arbitrary `pageId` and have `getOrCreatePageBackedInstagramAccount()` *create* a PBIA on any page the app token could reach. `/api/meta/adsets` **GET `?adSetId=`** fetches the ad set then asserts `act_<account_id>` is in the allow-list — it previously returned any ad set with no check. Meta IDOR checks fail closed on a missing `account_id` in `adsets.ts`, `ads.ts` AND `campaigns.ts` — `updateCampaign`/`deleteCampaign` were flipped from allow-on-missing to fail-closed on 2026-07-30 (they remain unreachable, with no route importing them). `MetaAd.account_id` and `MetaAdCreative.account_id` are typed optional while `MetaAdSet`/`MetaCampaign` type it required; the runtime checks lead with `!x.account_id`, which is correct for the optional case. The Snapchat equivalents deliberately still allow-on-missing because `SnapAdSquad`/`SnapAd` type `ad_account_id` as optional — where that is not acceptable, resolve the owner via the parent instead of failing closed (`/api/snapchat/ads` and `link-squad` both fall back to `getCampaign()`, since `SnapCampaign.ad_account_id` IS required). Meta Graph API base URL now lives in ONE place, `src/lib/meta/graph-version.ts` (`GRAPH_VERSION`/`GRAPH_BASE`/`OAUTH_DIALOG`), currently v25.0 — a version bump IS a one-line change; a version string anywhere else is a bug. All Meta API calls are server-side only via `metaFetch()` with Bearer auth and shared rate limiter.
- **`/api/data` is backed by Postgres (`user_metadata`), NOT blob storage (SEC-8, 2026-08-03).** It used to write `metadata/{googleUserId}/{key}.json` into the **public-read** `boilerroom-silo` store with `addRandomSuffix: false`, and an earlier version of this note called the paths "non-guessable … but not secret". They were not secret at all: `/api/auth/session` returns `googleUserId` to the browser. **Verified against production: every key returned HTTP 200 to an unauthenticated `curl`** — feed-provider configs (revenue-source mapping, ad account/page ids), presets (bid strategies, budgets, ROAS floors), articles, the Silo index, and the full build log.
  - **Postgres beat private-blob + signed reads because the entire consumer surface is server-side** — six call sites (`/api/data`, `/api/silo/delete`, `/api/catalogue/delete`, `lib/reporting/provider-network.ts`, `lib/meta/ad-limits-cache.ts`, `lib/meta/instagram-actor-cache.ts`) and **no client ever fetches a metadata blob URL** — so there was nothing to sign for. Do not "restore" a client-side read path.
  - **This also supersedes a wrong plan to move only the pixel ids.** Pixel ids are the *least* sensitive field in the store: a pixel id is embedded in the tracking JS of every page it fires on, so it is public by design. Moving only those would have left the genuinely sensitive records exposed.
  - `src/lib/db/user-metadata.ts` is the only accessor: `readUserMetadata(owner, key)` / `writeUserMetadata(owner, key, data)`. Reads are **DB-first with a one-time legacy blob fallback that self-heals into the DB**, so no cutover was needed — one dashboard load migrates every key because `KVHydrationProvider` reads them all. **Writes only ever go to Postgres**; writing the blob too would keep the exposure alive. `owner` is `'__global__'` (`GLOBAL_OWNER`) for the one cross-user cache (Instagram PBIA lookups), which real numeric Google ids can never collide with.
  - **JSONB does not preserve object key order** (keys are stored sorted) and collapses duplicate keys; **array order IS preserved**. Verified on the real production payloads that every key round-trips semantically identical and differs only in key ordering, which nothing depends on since all access is by name. **Never byte-compare or hash these payloads to detect change**, and never add a consumer that relies on insertion order — use an array if order must carry meaning.
  - The two **fail-closed ownership gates** (`/api/silo/delete`, `/api/catalogue/delete`) must keep distinguishing *"user owns nothing"* (empty set — authorizes nothing, valid) from *"could not establish ownership"* (`null` → 500). A malformed or unreachable store returns `null`, never an empty set.
  - Valid keys are still whitelisted in the route: `br_silo_assets`, `br_silo_tags`, `br_pixels`, `br_meta_pixels`, `br_presets`, `br_country_groups`, `br_feed_providers`, `br_articles`, `br_ad_accounts_v1`, `br_page_configs_v1`, `br_campaign_changelog`, `br_catalogue_v1`, `br_build_log`.
  - **Migrating the data remediates NOTHING on its own — the public blob copies must be DELETED.** `scripts/purge-public-metadata-blobs.ts` does that: it backs every blob up to `~/BoilerRoom-metadata-backup-<date>/` first, then refuses to delete anything whose migrated copy is not present and canonically matching, unless `--include-unmigrated` is passed. That flag exists for two legitimate cases — a `*_cache` key whose DB copy is *newer* (forcing `?refresh=1` leaves the blob stale), and the abandoned pre-Google **`snapUserId` (UUID) owner path**, whose snapshots are superseded (1 article vs 33, 3 Silo assets vs 218 when measured). Bundle it with esbuild like the other scripts and dry-run before `--write`.
- **`/api/feed-providers/channels/*` is user-scoped:** GET/POST/DELETE/PATCH pass `session.googleUserId` to all DB functions; queries filter by `google_user_id` so users can only access their own channels. `assignChannel`, `releaseChannel`, `normalizeChannelStatuses`, `updateChannelAdSquadId`, `getInUseChannelsByUser`, `getInUseChannelsWithoutSquadId`, `bulkForceChannelStatus`, and `updateChannelPausedStatus` all require `googleUserId` — never call them without it.
- **`/api/silo/delete` is user-scoped:** Before calling `del()`, the route fetches `metadata/{googleUserId}/br_silo_assets.json` from the blob store and verifies every URL to be deleted is present in the user's asset list. Fails safe (500) if the KV fetch fails.
- **`/api/silo/transcode` SSRF guard:** `blobUrl` is validated via Zod `.refine(isOwnBlobUrl)` before the server fetches it — same helper as `media/upload-from-blob` and `/api/meta/media`. The FFmpeg child gets `timeout: 240_000` and `maxBuffer: 8MB` (a crafted input could otherwise pin the 300s function), and the file extension is stripped to `/^[a-z0-9]{1,8}$/` before reaching a `/tmp` path — `fileName` is caller-supplied and unconstrained, so `x.mp4/../../evil` previously escaped `/tmp`. Keep the `execFile` argv-array form; never migrate to `exec` or add `shell: true`. Auth: `getSession()` + `isSessionValid()` (no ad account check needed — transcoding is user-scoped to their own Silo assets).
- **`media/upload` and `media/poll` require ownership checks:** Both routes call `isAdAccountAllowed` before forwarding to Snapchat.
- **`media/copy` checks both source and destination:** Both `sourceAdAccountId` and `destinationAdAccountId` must be verified to prevent cross-account media exfiltration. Error response uses `retryAsUpload` (not `orgMismatch`) — only set when the error string contains "different organization".
- **Chunked upload SSRF prevention (`pendingUploads` session field):** `media/upload-init` stores Snapchat-returned `addPath` and `finalizePath` in `session.pendingUploads[upload_id]` after the INIT call. `upload-chunk` and `upload-finalize` look up paths exclusively from the session — the client never supplies path values. This prevents an attacker from redirecting chunk or finalize requests to arbitrary URLs. The `pendingUploads[upload_id]` entry is deleted after finalize succeeds. **Correction (2026-07-29):** earlier notes claimed `..` / `://` / `@` guards live in this path. They do not. What actually exists is `toRelativePath()` in `media/upload-init`, which parses Snapchat's returned value and keeps only `url.pathname + url.search` — that discards host and userinfo, so it achieves the same end for the realistic threat model (the input is Snapchat's own API response, not user data). The `includes("/v1/")` test there is a normalisation step for regional paths, **not** a security guard, and must not be "tightened" to `startsWith` — that would break regional uploads. `upload-finalize` also now validates and authorizes *before* fetching an access token, so a rejected request no longer triggers an upstream token refresh on an unauthorized caller's behalf.
- **`media/upload-from-blob` SSRF guard:** `blobUrl` must satisfy `isOwnBlobUrl()` before server-side fetch. On 401 or 403 from Snapchat, the route refreshes the access token and retries once before failing — Snapchat returns 403 E3002 on expired tokens (not just genuine permission failures); fresh `FormData` is constructed for the retry since the first request body stream is consumed.
- **Visymo pagination SSRF guard:** `page.next` URL is validated to originate from `https://partnerhub-api.kingsroad.io` before following. Loop aborts on unexpected origin or invalid URL.
- **Reporting date range validation:** `/api/reporting/sync` Zod schema enforces YYYY-MM-DD format and a maximum 90-day window. `/api/reporting/combined` and `/api/reporting/drilldown` enforce a 366-day cap after format validation. Requests outside these ranges return 400.
- **`/api/reporting/cron-sync` is cron-authenticated:** `verifyCronSecret` uses Node.js `timingSafeEqual` to compare the `Authorization: Bearer {CRON_SECRET}` header against `process.env.CRON_SECRET`; returns 401 on mismatch. Vercel auto-injects `CRON_SECRET` on Pro plans and sends it on every scheduled invocation.
- **Stored platform tokens are AES-256-GCM encrypted at rest under `TOKEN_ENCRYPTION_KEY`, NOT `SESSION_SECRET` (SEC-15, 2026-08-03).** `user_snapchat_tokens.refresh_token_enc` and `user_meta_tokens.access_token_enc` hold ciphertext, never plaintext. The key used to be the first 32 bytes of the hex-decoded `SESSION_SECRET`, which meant one leaked env var yielded **both** forged session cookies and every stored OAuth credential — different blast radii sharing one secret (a forged cookie dies with the 14-day cookie `maxAge`; a decrypted refresh token is durable against the ad platform). `src/lib/db/token-crypto.ts` now reads **two** formats and writes the strongest key available:
  - legacy `base64(iv):base64(tag):base64(ct)` → `SESSION_SECRET`-derived key
  - v2 `v2:base64(iv):base64(tag):base64(ct)` → `TOKEN_ENCRYPTION_KEY`

  Dual-read is what let this ship without a flag-day cutover; the explicit version prefix (rather than trial-decrypting with each key) keeps the choice deterministic and makes progress a plain string query: `SELECT count(*) FROM user_snapchat_tokens WHERE refresh_token_enc NOT LIKE 'v2:%'`. **Do not delete the legacy branch until that returns 0 for BOTH token tables** — a pre-backfill row is only recoverable through it. `TOKEN_ENCRYPTION_KEY` unset falls back to legacy, so a dev box without the variable keeps working.
  - **`scripts/reencrypt-tokens.ts` is the backfill, and it runs in both directions.** Bundle with esbuild (`--alias:@=./src --packages=external`, outfile inside the repo so `node_modules` resolves), then `node --env-file=.env.local scripts/.reencrypt-tokens.mjs [--write] [--to-legacy]`. Dry run is the default. Each row is decrypted, re-encrypted, and decrypted **again** and compared to the original plaintext before any UPDATE is issued; the UPDATE is guarded on the old ciphertext still being present, so a concurrent OAuth callback is never clobbered with a stale value; failures are isolated per row so one undecryptable row does not stop the sweep.
  - **Ordering is the hazard, and `--to-legacy` exists because of it.** Every environment that reads these rows must hold `TOKEN_ENCRYPTION_KEY` *before* the rows become v2, or that environment throws on every token read and the cron silently skips all tenants (reporting stales; no corruption, no token loss). Set the variable → deploy → *then* backfill.
  - **Vercel gotcha that cost real debugging time: Production/Preview env vars are SENSITIVE (write-only) by default, so `vercel env pull` returns them BLANK.** That is expected, not a mangled value — do not conclude the variable is empty and start rolling back (I did). Verify against **Development** (not sensitive by default) to confirm a value stored correctly, then verify Production **behaviourally** — for this key that means watching `report_sync_log.last_synced` advance past the next `:15`/`:46` cron, since a failed decrypt means no sync row is written at all. Also note `vercel env add` **via piped stdin can store an empty value**; use `--value "$KEY" --force --yes`, which is verified to work. `CRON_SECRET` is sensitive too, so the cron cannot be triggered manually for this check.

  Only the Snapchat *refresh* token is persisted — its access token is obtained at runtime by the cron via token exchange and never stored. An attacker now needs the DB dump **and** `TOKEN_ENCRYPTION_KEY` to obtain usable tokens. Token lifecycle: written on Snapchat OAuth callback and on token refresh, deleted on Snapchat disconnect. Ad account IDs (`{id, timezone}[]`) are updated in the same table whenever `/api/snapchat/ad-accounts` is called, keeping the cron's account list current.
- **`/api/auth/refresh` skips Snapchat when token is still valid:** Pre-check compares `session.snapExpiresAt` against now − 5 min; returns `{ ok: true, cached: true }` without hitting Snapchat's token endpoint.
- **Session cookie has `maxAge: 14 days`:** Prevents indefinite persistence on shared machines. iron-session resets the clock on every `save()`.
- **Snapchat token revoked on disconnect:** `/api/auth/snapchat/disconnect` calls Snapchat's `revoke_token` endpoint (best-effort) before clearing the session fields.
- **Snapchat error bodies are not forwarded verbatim:** Routes `console.error` full details and return generic codes to the client (`"upload_failed"`, `"internal_error"`, etc.). The adsquads PATCH handler specifically checks whether the error message starts with `"Snapchat API error"` (raw HTTP body from `snapFetch`) and replaces it with `"snapchat_request_failed"` — only structured sub_request_error_reason strings (e.g. `"E2025: ..."`) are returned to the client.
- **Content Security Policy lives in `src/proxy.ts`, NOT `next.config.mjs` (per-request nonce, 2026-08-03).** `script-src` is `'self' 'nonce-<128-bit random>' 'strict-dynamic'`, plus `'unsafe-eval'` in dev only (webpack Fast Refresh). `'unsafe-inline'` is gone — it told the browser to execute any inline `<script>` it found, which is the payload half of most XSS.
  - **Never re-add a CSP to `next.config.mjs`.** Its headers are static, so a nonce is impossible there — and two CSP headers are enforced *independently* with a script having to satisfy both, so a leftover copy silently subtracts from the proxy's policy instead of overriding it.
  - **Next stamps the nonce onto its own bootstrap/hydration `<script>` tags by reading the CSP off the REQUEST**, which is why the proxy sets `Content-Security-Policy` on `requestHeaders` and not just the response. There are no hand-written inline scripts in `src/` (no `next/script`, no `<script>`, no `dangerouslySetInnerHTML`), so nothing else needs threading. A future inline script must read `headers().get('x-nonce')` and set the tag's `nonce` prop, or it will be blocked.
  - **The root layout sets `export const dynamic = "force-dynamic"` and that is load-bearing.** A prerendered route is built with no request in scope, so its inline scripts carry no nonce and the browser blocks them at runtime — the page loads with no JS and never hydrates. `/callback`, `/privacy` and `/_not-found` were static before this; everything else was already dynamic. Removing that export silently breaks whichever routes Next decides to prerender.
  - **The matcher widened from `/api/:path*` to `["/((?!_next/static|_next/image|favicon.ico).*)"]`.** A document route left out of the matcher gets **no CSP at all**, which is worse than the `'unsafe-inline'` this replaced — only ever add exclusions for non-HTML assets. Side effect: the SEC-26 Origin check now also covers page POSTs (no server actions exist, so nothing legitimate is affected).
  - **`'strict-dynamic'` makes supporting browsers ignore `'self'` for scripts** and instead trust whatever an already-trusted script loads — that is what lets webpack fetch its chunks. `'self'` stays only as a fallback for browsers without strict-dynamic support. **Scope caveat:** strict-dynamic by design still permits scripts created by trusted code, so this closes HTML-injection XSS (parser-inserted `<script>`, verified blocked) but *not* DOM-XSS sinks that call `createElement('script')`.
  - **CVE-2026-44581 / GHSA-ffhc-5mcf-pf4q is PATCHED as of the Next 16.3.0 upgrade (2026-08-04), and was additionally never exploitable here.** The advisory ("cross-site scripting in App Router applications using CSP nonces", affected `>=13.4.0 <15.5.16`, patched 15.5.16 / 16.2.5) covers a malformed `Content-Security-Policy` **request** header being reflected into rendered HTML behind a shared cache. Adopting nonces on 14.2.35 is what brought this app into scope; 16.3.0 takes it back out. Keep both layers:
    - **The framework fix is now the primary defence.** Do not downgrade below 16.2.5 while nonces are in use.
    - **The proxy overwrite remains the belt-and-braces layer** and is exactly the mitigation the advisory recommended for un-upgraded apps. `requestHeaders.set("Content-Security-Policy", csp)` uses `Headers.set()`, which **replaces** any inbound value, so an attacker-supplied header is discarded on every request reaching the proxy. **Do not "optimize" that `set` into a conditional, and never switch it to `append`** — either would remove the mitigation, and `append` would additionally create a second policy that intersects with the first (see the two-policy warning above).
    - Verified against a production build, not by reasoning alone: injecting `Content-Security-Policy: script-src 'nonce-xyz"><script>alert(1)</script>'` on `/login`, `/privacy`, `/callback`, `/dashboard/performance` and a 404 returned **exactly 1** CSP header each, carrying a fresh server-generated nonce, with neither the payload nor the attacker's nonce anywhere in the HTML. Re-run that check after any proxy change.
    - The matcher's exclusions (`_next/static`, `_next/image`, `favicon.ico`) are safe here only because none of them render HTML with a nonce. **Any exclusion that can return a document would bypass this overwrite** as well as losing the CSP entirely.
  - **`style-src` keeps `'unsafe-inline'` deliberately:** Next injects inline `<style>` during hydration and route transitions, those cannot be nonced the way scripts can, and injected CSS does not execute.
  - `img-src` allows `'self' data: blob: https://*.public.blob.vercel-storage.com https://lh3.googleusercontent.com` — add new external image domains here or they are silently blocked. `connect-src` gains `ws: wss:` in dev for the HMR socket. `worker-src` is `'self'` only (see the ffmpeg.wasm note above).
- **`src/middleware.ts` was renamed to `src/proxy.ts` on 2026-08-05, and the exported function is now `proxy`.** Next 16 deprecated the `middleware` convention (`v16.0.0`) in favour of `proxy`. This was deliberately deferred during the 2026-08-04 upgrade and done later as its own change, because it is **not** a pure rename: **`proxy` runs on the Node runtime only, the `runtime` config option is not available in a proxy file, and setting it throws** (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`). Edge is therefore not recoverable without reverting the rename.
  - **The tradeoff that was accepted:** this file runs on *every* non-asset request and does three security jobs (CSP nonce, SEC-26 Origin check, rate limiting). It now runs a Node function in front of essentially the whole app instead of executing at the edge, which changes the latency and cold-start profile. **Narrowing the matcher is not a safe way to claw that back** — excluding a document route leaves it with no CSP at all, and excluding an API route drops its Origin check.
  - The in-memory rate-limit Map is now per-Node-instance rather than per-Edge-instance. Same guarantee in kind (never distributed), but instance lifetime and count differ, so observed limits may be looser or tighter than before. Exactness still requires a shared store, which was equally true on Edge.
  - **Verified after the migration**, all against the Node runtime: three consecutive `/login` requests returned three *different* nonces; cross-site `POST` and an unparseable `Origin` both 403 while a foreign-`Origin` GET stayed 200; `/api/silo/transcode` gave 5 × 405 then 429 with `Retry-After: 60`, proving module state survives between requests; `/api/reporting/cron-sync` × 25 and `/api/reporting/sync-status` × 25 produced zero 429s, confirming the cron bypass and that `sync-status` still matches its own 60/min bucket ahead of the 20/min `sync` prefix. `next build` reports `ƒ Proxy (Middleware)`. Re-run all of these after any change to this file.
- **Rate limiting (`src/proxy.ts`):** the proxy applies **per-class budgets**, not just auth — it previously covered `/api/auth/*` only, leaving native FFmpeg (300 s), the reporting sync fan-out (300 s), in-memory zipping, and unbounded `/api/data` writes with no request-rate control. Returns 429 with `Retry-After`. Keyed on the **bucket prefix**, not the raw path, so ids in the path cannot mint a fresh allowance. Per-instance in-memory Map with eviction above 10k keys — not a distributed guarantee, but effective against sustained single-IP abuse. Runs on the **Node** runtime since the 2026-08-05 proxy rename, so "per-instance" now means per Node instance. Current budgets per 60 s unless noted: `silo/transcode` 5 · `meta/ad-media` 10 · `meta/ad-limits` 15 · `meta/page-ad-counts` 20 · `reporting/sync-status` 60 · `reporting/meta-sync` 20 · `reporting/sync` 20 · `auth/` 20 · `snapchat/media/upload-chunk` 600 · `silo/upload` and `catalogue/upload` 60 · `data` 120. **BUCKETS order matters** — first matching prefix wins, so `reporting/sync-status` must stay ahead of `reporting/sync`. The two 3-per-5-min diagnostic buckets were removed on 2026-08-04 with the debug routes.
  - **`BUCKETS` order is load-bearing** — the first matching prefix wins. `"/api/reporting/sync"` is a prefix of `"/api/reporting/sync-status"`, so sync-status must stay listed first or the dashboard's mount-time poll inherits the sync trigger's 20/min budget.
  - **`upload-chunk` is deliberately loose at 600/min.** It sends 4 MB per request (Vercel's 4.5 MB payload ceiling), so one 500 MB video is ~125 requests and a multi-video launch legitimately reaches the hundreds. A false 429 there corrupts an in-flight upload — tune it up, never down.
  - **`/api/reporting/cron-sync` is explicitly exempt** (early return, before bucket matching). It is authenticated by `CRON_SECRET`, and a false 429 silently staleing every tenant's reporting is worse than anything the limit prevents.
  - The matcher is intentionally **broader** than `BUCKETS` so adding a budget needs no matcher edit; matched-but-unbucketed paths fall straight through. Enumeration protection for id-guessing surfaces is **not** handled here — IP buckets are the wrong layer for it; that lives in the per-resource authz checks on those routes.
