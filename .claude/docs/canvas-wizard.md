# Canvas Wizard, Synthesis & Submission

The canvas → synthesis → orchestrator → platform pipeline, plus URL and naming macros.

- **Canvas wizard:** `WizardShell` renders in three modes: `canvas` (`CampaignCanvas` React Flow), `review` (`ReviewAndPost`), `done` (success screen). The done screen displays a `launchError` state (set on any unhandled submission throw, reset by "New Build") so launch failures are visible instead of silently swallowed. `CampaignCanvas` is loaded via `next/dynamic` with `ssr: false`. The canvas uses `useCanvasStore` (Zustand) to track `creativeRows: CreativeRow[]` (each row holds an ordered list of `groupIds`), `creativeGroups: CreativeGroup[]` (each group holds 1–5 asset IDs), five edge lists (`rowToProvider`, `providerToTrafficSource`, `providerToArticle`, `articleToPreset`, `articleToAdAccount`), `nodePositions`, `routerNodes`, and `expandedArticleIds: Set<string>` (toggled by `toggleArticleExpanded(nodeId)` — a new Set reference on every change triggers the expansion-aware re-layout useEffect). Chain: **Row → Provider → TrafficSource (one node per active platform) → Article → AdAccount → Preset**, with Router (when present) sitting between Row and Provider only. `buildCampaignMatrix()` iterates `rowToProvider` edges → for each row iterates `row.groupIds` → each group produces one `CampaignBuildItem` per article/preset/account combination, with `creativeIds: string[]`. `providerToArticle` carries a `platform: "snap"|"meta"` field — picking an article under a provider's Snap `TrafficSourceNode` and picking it under Meta are independent edges (independent headline content, independent downstream wiring), not one shared pick. `articleToAdAccount`/`articleToPreset` key only by `articleId` (not platform), so since the same articleId can carry independent Snap and Meta picks, every join against them (`buildCampaignMatrix`'s `eligibleAccounts`, and `CampaignCanvas`'s AdAccount→Preset edge rendering) additionally filters accounts by their own platform matching the current article edge's/preset's platform — otherwise a Meta account sharing that articleId would wire to Snap content and vice versa. Cascade: removing a row→provider edge that orphans a provider also removes all of its `providerToArticle` edges (every platform) via `cascadeProviderRemoval()`, cascading each through `orphanArticleForPlatform()` (drops only that edge's platform's `articleToAdAccount`/`articleToPreset` entries — an account's platform from its `AdAccountConfig`, a preset's from its own `trafficSource` — leaving the other platform's wiring for the same article untouched), plus its `providerToTrafficSource` entries; toggling a traffic source off (via the Provider card's button, or a `TrafficSourceNode`'s "in" handle) prunes (via `pruneTrafficSource()`) exactly the `providerToArticle` edges matching that platform, cascading each the same way. On launch, `WizardShell` loads all assets for `item.creativeIds`, calls `synthesizeCampaign()`, then `runSubmission()`.

  **Creative row concept:** A `CreativeRow` is the top-level canvas unit — one row node, one shared React Flow handle, connects to one or more providers. Each card slot in the row = one `CreativeGroup` = one ad set. Within a group, multiple creatives = multiple ads in that ad set. Node ID prefix: `row-{id}`. Cards render left-to-right; `groupIds` is prepend-on-add so `groupIds[0]` = newest = leftmost, `groupIds[last]` = oldest = rightmost. Each time a slot is prepended the node's x position is decreased by `ROW_CARD_STEP = 172` (160 + 12) to keep the rightmost card anchored at the same canvas position. A slot with 2–5 creatives shows a clickable **×N badge** that opens an inline overlay; each mini-thumbnail has a ✕ to remove that creative. Each slot column has a always-visible "＋ Add creative" button below it. Row actions live in an always-visible **side dock** (⊞ Add slot, 🔗 Provider, ↓ New row, ⧉ Duplicate, ✕ Remove row) that is part of the node's layout between the cards and the handle. `nodeWidth = rowWidth + DOCK_LEAD (32) + DOCK_W (142) + DOCK_TO_HANDLE (22)` — this ensures the handle (always at `Position.Right`) anchors past the dock so provider edges never overlap it. Multi-creative slots show stacked colour-coded name pills (blue→indigo→violet… palette). Max 8 slots per row, 5 creatives per slot. **Catalogue (Collection Ads) rows behave identically to normal rows** — they pick a hero Silo asset like any other slot; the catalogue-ness comes entirely from the connected preset (`preset.isCatalogue`), not from the canvas. There are no empty/placeholder slots and no special "add catalogue slot" path.

  **React Flow canvas (`CampaignCanvas.tsx`):** Nodes are **not draggable** (`nodesDraggable={false}`); all positions are owned entirely by auto-layout. Key design decisions:
  - **Creative rows** — the empty-state button and `openAddCreative` create a new row then open SiloBrowser. Canvas tracks two Silo targets: `targetRowId` (add new slot to row) and `targetGroupId` (add creative to existing slot). On select, routes to `addGroupToRow` or `addCreativeToGroup` accordingly. Empty row is removed on Silo cancel. No top-bar "+ Add Creative" button.
  - **Provider visibility** — providers only appear after at least one row exists.
  - **Traffic Source step** — Snap/Meta toggle buttons live on `ProviderNode` itself (`selectedTrafficSources` + `onToggleTrafficSource` data props). Toggling a platform on spawns a dedicated `TrafficSourceNode` (id `ts-{feedProviderId}-{platform}`) — up to two independent sibling nodes per provider, not one combined node. Each has its own always-visible "＋ Pick articles" link, filtered to `article.trafficSources` matching *that node's single platform* (not a union). A fixed, non-deletable edge (`provider-{id} → ts-{id}-{platform}`) connects each active node to its provider. Picking an article is a genuinely independent action per platform: `providerToArticle` edges carry a `platform` field, so picking the same article from the Snap picker and the Meta picker creates **two separate edges**, each rendering its own `article-{id}-{platform}` node (`buildNodes` iterates `providerToArticle` directly, one node per edge) — never a single node shared between platforms. `parseTsNodeId()`/`parseArticleNodeId()` recover `{feedProviderId, platform}`/`{articleId, platform}` from node ids wherever needed (`onConnect`, `onEdgesDelete`, `makeDisconnectTarget`, `isValidConnection`). Wiring an article to an ad account requires an actual same-platform `providerToArticle` edge (checked in `onConnect`/`onEdgesDelete`/`isValidConnection`), not just that the article's own `trafficSources` includes that platform. Toggling a platform off (Provider card button, or the `TrafficSourceNode`'s own "in" handle — both call `toggleProviderTrafficSource`) removes that node and prunes only that platform's `providerToArticle` edges via `pruneTrafficSource()`.
  - **Auto-router** — in `onConnect`, when a provider already has ≥1 article edge (across either platform) and no router yet, a router is auto-inserted between Row and Provider (row-side fan-in declutter only — it does **not** sit between TrafficSource and Article; with up to two independent platform nodes per provider there's no single node for it to attach to on the article side, so `TrafficSource → Article` edges always source directly from the specific `ts-{id}-{platform}` node). No manual "+ Router" button on ProviderNode.
  - **Explicit article→account wiring** — users drag from article's right handle to an account's left handle. `store.edges.articleToAdAccount` stores these edges. No global `selectedAdAccountIds` broadcast. **Cross-provider connections are blocked** at the React Flow drag level via `isValidConnection`: an article can only connect to an account whose `adAccountConfig.feedProviderIds` includes the article's `feedProviderId` (accounts with empty `feedProviderIds` are permissive for backward compat). Same rule applies to account→preset: `preset.feedProviderId` must be in `cfg.feedProviderIds`. The `onConnect` account→preset handler only wires `articleToPreset` edges for articles already connected to the specific account (not all active articles), so a Vizymo account cannot pull in Predicto articles.
  - **Left handle click = disconnect** — all target handles have an `onClick` that calls `makeDisconnectTarget(nodeId)`, which removes all incoming edges for that node (cascade-safe).
  - **Preset gate** — preset nodes are **hidden entirely** (not just disabled) until `store.edges.articleToAdAccount.length > 0` (`canSelectPresets`). `visiblePresets` returns `[]` when `canSelectPresets` is false.
  - **Edges** — `ProviderEdge` renders a single right-angle turn per edge (`getOrthogonalPath` — straight out of the source, one rounded corner-pair (radius 10, capped by available space) down/up to the target's row, straight into the target; a plain straight line when source/target share a y; edges always flow left-to-right column-wise so x never moves backward — replaces the earlier cubic-bezier `getMidpointBezierPath` midpoint S-curve) as two raw SVG paths: a wide blurred halo (`strokeWidth 8`, `opacity 0.18`) layered beneath a crisp main stroke (`strokeWidth 2.5`, `opacity 0.85`); both in provider color. Selected state bumps to `12`/`3` and full opacity. Row handles (on `CreativeGroupNode`) are 28px white circles (`!w-7 !h-7 !rounded-full !bg-white !border-[3px] !border-gray-700`). Article/Account/Preset nodes use **H2 Ghost Ring handles**: 14px dark fill (`!w-3.5 !h-3.5 !bg-gray-900`) with a `border: 2px solid {providerColor}` and `box-shadow: inset 0 0 5px {color}50, 0 0 8px {color}45` (inner+outer glow) when the node is connected; gray ring (`#374151`) when disconnected.
  - **Provider swim lanes** — `LaneOverlay` (rendered as a child of `<ReactFlow>`, below `<Controls>`) draws one translucent band + name label per provider, sized from a `laneBounds` memo in `CampaignCanvas`. The **x-range is global** — one shared min/max computed across every non-`group` node currently on the canvas, used for every lane's band — so a provider with no content yet in a later column doesn't get a band (and divider) that stops short of the full flow width. The **y-range is per-provider**, from the live `nodes` state using the shared `providerIdForNode`/`nodeHeightFor` classifiers (also used by `handleAutoLayout`'s hard-band enforcement, so the two can never disagree). **Row (`group`) nodes are deliberately excluded from both the x-range and y-range** — a single row can fan into multiple providers (`connectRowToProvider` supports 1+ providers per row), so it isn't owned by any one lane; including it in the x-range was dragging every lane's band out to visually stretch behind the creative cards (row nodes sit at `x: 0`, left of every other column). For accounts/presets whose real provider id is empty (`feedProviderId ""` / `feedProviderIds []` — a currently-reachable state, not legacy-only, since neither the preset nor ad-account forms require it), `laneBounds` falls back to `fallbackLaneProviderId` (`CampaignCanvas.tsx`, next to `providerIdForNode`), which picks the first active provider matching the node's platform (same predicate `visiblePresets`/`visibleAccounts` use for visibility) so the node still lands inside a real lane instead of floating in the untinted gap between lanes; meta ad accounts are not attributed this way since `metaAllowedIds` isn't tied to one provider. A dashed divider (opacity fades 0%→12%→0% along its length, via an SVG `linearGradient`) separates adjacent lanes, **skipped if the two lanes' y-ranges still overlap** (defensive only — shouldn't trigger now that `handleAutoLayout` guarantees non-overlap); a shorter vertical divider of the same style sits between a provider's two Traffic Source nodes when both Snap and Meta are active, positioned at the horizontal midpoint between the Provider and Traffic Source columns. Uses `useViewport()` to convert flow coordinates to screen pixels — purely decorative, never added to the `nodes` array, so it cannot affect `fitView`'s bounding box. Column-locking across lanes (every tier at one shared x regardless of provider) was already provided by `dynColX`; non-overlap between providers *and* between a provider's own Snap/Meta content is a hard guarantee enforced in `handleAutoLayout` (see Auto-align below — now via a sort tiebreaker + centering refinement rather than a rigid band shift), not just a visual inference. See "Unassigned" nodes under Auto-align for the `orphanDividers` sub-divider LaneOverlay also draws.
  - **Router node** — sleek 36px circle with ⑃ icon (was diamond).
  - **Auto-align (Option A2 — center-anchored tree)** — dagre LR with `ranksep: 200`, `nodesep: 60`; row node dims estimated `340×285`. Fires automatically on every structural change (edges added/removed, nodes shown/hidden) via `useEffect(() => { handleAutoLayout(); }, [handleAutoLayout])`, and on every article expansion change via a second `useEffect(() => { handleAutoLayout(); }, [expandedArticleIds, handleAutoLayout])`. The "⊞ Auto-align" toolbar button is a manual re-trigger. After dagre runs, `handleAutoLayout` computes **dynamic column X positions** (`dynColX`) as `P = maxRowHandleX + 120` where `maxRowHandleX = max(storedX + nodeWidth)` across all rows — using the actual stored x position (which shifts left on every card prepend) rather than the raw node width, so the 160px gap between handle and provider is consistent regardless of how many slots each row has. The static `COLUMN_X` constant is only used outside `handleAutoLayout` for initial placement. `computeAutoLayout` (in `CanvasControls.tsx`) accepts `expandedArticleIds?: Set<string>` and uses `ARTICLE_EXPANDED_H = 230` instead of `NODE_HEIGHT = 90` for expanded article nodes in dagre, giving them correct vertical space.

    Y-positioning is a **bottom-up, center-anchored refinement**, not a rigid band-shift: a shared `resolveColumnCollisions(nodeIds)` helper sorts a node-type column by `(nodePriority — provider creation order, platformRank — Snap=0/Meta=1/unattributed=0.5 via `platformForNode`, isOrphan — connected-before-not-yet-wired, y)` and pushes each node down to clear the previous one + a height-aware min gap (`ARTICLE_EXPANDED_H + 20`/`GROUP_CARD_H + 20`/`ROW_GAP = 130`, with an extra +30 section gap when an orphan follows a connected sibling). This guarantees provider ordering and Snap-before-Meta *within one column*, but not that the two platforms' combined vertical ranges stay non-overlapping *across* the article/adaccount/preset columns together — see the restored band-separation pass below for that. It's run once for every column as a base/leaf layer (presets have no children, so this is their final position), then a **centering pass** walks columns `["adaccount", "article", "ts", "provider"]` (leaves→root) using a `childrenMap` built from the actual rendered `currentEdges`: any node with ≥1 positioned child re-centers its y on the midpoint of those children's y (a lone child aligns exactly with its parent); a node with no children yet (e.g. a freshly-toggled traffic source with no articles picked) keeps its existing position rather than collapsing to 0 — **except `article`**, where a childless article instead aligns with its own `ts` parent's y (`currentEdges.find(e => e.target === id)?.source`), since otherwise it would keep dagre's raw pre-refinement guess with no relationship to which platform's row it belongs to. Each column is re-run through `resolveColumnCollisions` after centering to fix any overlap the re-centering introduced. The practical effect: connecting/disconnecting an edge only ever moves that one branch (no more shifting unrelated siblings, no leftover gaps on disconnect — this replaced the old sequential-list + two-`enforceBands`-pass approach, which shifted a whole lane on connect and never compacted on disconnect). Disconnected-but-visible providers are anchored relative to the nearest connected provider (±`ROW_GAP` per slot); their accounts/presets are seeded per (type, provider, platform) group *after* the centering pass above (`anchorYFor`, seeding any earlier would anchor to dagre's raw pre-refinement guess instead of where ts/article actually end up) at the average y of that provider+platform's own connected article node(s) — falling back to that platform's `ts-{providerId}-{platform}` row, then the global article-range midpoint, if no article exists yet — rather than one shared midpoint for both platforms; a merge-back `resolveColumnCollisions` pass then re-resolves the `adaccount`/`preset` columns with the freshly-seeded orphans included. A **per-provider Snap/Meta band-separation pass** then runs, reusing the generic `enforceBands` helper (id-list based, not column-specific) across all three columns together (`article`+`adaccount`+`preset` ids grouped by `(providerId, platform)`, gutter 60) — this is the cross-column non-overlap guarantee the column-level sort alone can't provide (reinstates what used to be a per-column "Pass B", generalized). Finally, a single `enforceBands(sortedByCreation, byProviderNodeIds, positions, heightForId, 100)` pass runs last, purely so `LaneOverlay`'s per-provider band *rectangles* (which span every column) never visually overlap. Final placement of orphans is governed by the orphan-aware sort — see "Unassigned" nodes below. `ArticleNode` expansion state is stored in Zustand (`expandedArticleIds`) instead of local React state so the layout system can observe it.

  - **"Unassigned" nodes** — an ad account or preset that's visible (provider+platform active, per `visibleAccounts`/`visiblePresets`) but has no edge at all (`isOrphan` in `handleAutoLayout` — absent from `connectedIds`) sorts to the bottom of its platform group in its column (via the `isOrphan` tiebreaker in `resolveColumnCollisions`, plus the extra +30 gap after the last connected sibling) instead of being centered by the tree-refinement pass (orphans have no children/parent, so they're simply excluded from centering and keep their seeded position). That seed is platform-specific: `anchorYFor` anchors each orphan to the average y of its own provider+platform's connected article node(s) — falling back to that platform's `ts-{providerId}-{platform}` row, then the global article-range midpoint (grouped by `(type, provider, platform)` via `orphanGroupKey`, spread with `ROW_GAP` when several share a group) — so a Snap orphan lands directly in front of its provider's Snap article(s) and a Meta orphan in front of the Meta article(s), not both hovering around one shared midpoint regardless of platform. `AdAccountNode`/`PresetNode` render this state with a dashed border, reduced opacity, and an italic "unassigned" sub-label (derived from each node's own existing local `connected` check — no new data threading). `LaneOverlay`'s `laneBounds` memo (`CampaignCanvas.tsx`) independently computes, per provider lane, per column (`adaccount`/`preset`), *and per platform*, the seam between the max-Y of that platform's connected nodes and the min-Y of its orphans (same local edge-based connectedness check as the node components) and exposes it as `LaneBound.orphanDividers`; `LaneOverlay` draws a plain (non-fading, to distinguish from the lane/branch dividers) dashed line + small "Unassigned" label for each — Snap and Meta each get their own seam marker, never a single shared one.
  - **Canvas** — dark background `#1f2937`, `fitView` with `padding: 0.3, maxZoom: 1.0`.

  **React Flow render-loop hazards (React error #185):** Four pitfalls that cause an infinite `setNodes` loop:
  1. **`store.nodePositions` must NOT be in `buildNodes` deps.** Fix: read positions via `nodePositionsRef` (a `useRef` kept in sync via a separate `useEffect`) so `buildNodes` can read current positions without subscribing to them.
  2. **`nodesDraggable={false}` is set on `<ReactFlow>`** — drag is disabled entirely. `onNodesChange` no longer writes positions to the store. Do NOT re-enable dragging; it conflicts with auto-layout and caused nodes to migrate unpredictably. The old hazard note (use `change.dragging === false` strict check) is moot with drag disabled but kept here for context.
  3. **Never inline `[]` as a fallback in hooks that feed into `buildNodes` deps.** `useAdAccounts` returns `data?.accounts ?? EMPTY_ACCOUNTS` where `EMPTY_ACCOUNTS` is a module-level constant. Inline `[]` creates a new reference every render while SWR is loading → `visibleAccounts` recomputes → `buildNodes` rebuilds → `setNodes` → re-render → repeat.
  4. **Callbacks in `buildNodes` deps must NOT close over the whole `store` object.** `store` gets a new reference on every Zustand state update (including `setNodePositions`). Any `useCallback` with `[store]` in deps that feeds into `buildNodes` deps will cause an auto-layout loop: `setNodePositions` → new `store` → callback changes → `buildNodes` changes → auto-layout fires → `setNodePositions` → repeat. Fix: use `useCanvasStore.getState()` inside the callback body so it reads current state without subscribing. `makeDisconnectTarget` uses this pattern and has empty deps `[]`.
  Visibility arrays (`activeProviderIdsFromArticles`, `visibleAccounts`, `visiblePresets`) are wrapped in `useMemo`. Articles no longer have a `visibleArticles` memo — `buildNodes` iterates `store.edges.providerToArticle` directly, one node per edge (id `article-{articleId}-{platform}`), so an article's node(s) only exist for platforms it was actually picked for. The "＋ Pick articles" button lives on each `TrafficSourceNode` (not `ProviderNode`), always visible since the node's existence already implies a platform is selected; clicking it opens the checklist modal (`articlePicker: {providerId, platform}` state), filtered to `article.trafficSources` matching *that specific platform*, with its checked state and its toggle call both scoped to that exact platform (`selectedIds` filters `providerToArticle` by `platform` too, and the click handler passes `platform` to `toggleProviderToArticle`) — picking the same article from the Snap and Meta pickers are independent actions, each producing its own edge/node. `visibleAccounts` and `visiblePresets` are additionally gated by `providerHasTrafficSource(providerId, platform)` (a memoized helper reading `store.edges.providerToTrafficSource`) so only accounts/presets matching an active provider's *selected* platform(s) appear — e.g. a Meta account only shows once some active provider has explicitly picked "Meta", not merely because it has a picked article. **Node ordering:** the article loop in `buildNodes` sorts `providerToArticle` edges by `sortedByCreation` provider index before assigning initial y-positions (`index * ROW_GAP`), same as `visibleAccounts`/`visiblePresets`, so nodes connected to the top provider always appear at the top of their column. `computeAutoLayout` also post-processes dagre's output to re-sort within each x-rank by average upstream y, cascading the fix through the full chain. A `nodePriority` map (provider creation index) is passed as a tiebreaker — when a router and a sibling provider land in the same dagre rank with identical avgUpstreamY (both connect from the same row), the tiebreaker ensures provider[0]'s nodes always sort above provider[1]'s across the entire right-side cascade.

  **Canvas visual rules:**
  - **Provider colors** — assigned from `PROVIDER_COLORS` array indexed by sort-order of `createdAt` (stable; not array position). Colors propagate to node borders, indicator dots, and SVG edges.
  - **Vivid Flow node backgrounds** — connected nodes (`ArticleNode`, `AdAccountNode`, `PresetNode`) use `background: linear-gradient(135deg, {color}18 0%, #111827 65%)` with `boxShadow: 0 4px 24px {color}25` for a colored drop-shadow. `ProviderNode` uses a slightly stronger gradient (`{color}22 → #111827 70%`) plus an inset color ring via `boxShadow: 0 4px 24px {color}20, inset 0 0 0 1px {color}20`. Disconnected nodes fall back to the standard `dark:bg-[#111827]` solid surface.
  - **CreativeGroupNode (row node)** — horizontal flex row of portrait cards (`160×285px` each, `9/16` aspect). Left accent stripe per card shows connected provider color(s). Node outer div has `style: { background: "transparent", border: "none", padding: 0 }` to override the React Flow node wrapper background. `groupIds` is rendered without reversal; `groupIds[0]` (newest) is leftmost, `groupIds[last]` (oldest) is rightmost. Each prepend subtracts `ROW_CARD_STEP = 172` from the node's stored x so the rightmost card stays anchored. `nodeWidth = rowWidth + DOCK_LEAD + DOCK_W + DOCK_TO_HANDLE` — wider than the cards area to fit the side dock; handle sits at the new right edge past the dock. Single-asset slots show a frosted white name pill; multi-asset slots show stacked coloured pills indexed into `CREATIVE_NAME_COLORS` (blue→indigo→violet…).
  - **Ad account NodeCard** — connected state derived from `articleToAdAccount` edges (not from `selectedAdAccountIds`). Shows 2-letter initials avatar + platform badge (yellow Snap ghost / blue Meta "f"). `CampaignCanvas` merges `useAdAccounts()` (Snap) and `useMetaAdAccounts()` (Meta) into a unified `CanvasAdAccount[]` array with `platform: "snap" | "meta"`. Cross-platform wiring blocked in `isValidConnection`: Meta accounts can only connect to `trafficSource: "facebook"` presets and vice versa; article→account connections are additionally gated on `article.trafficSources` (see Articles section) — checked in both `isValidConnection` (drag-time block) and `onConnect` (defense in depth), both using the already-merged `allAccounts` platform lookup.
  - **Preset gate** — `disabled` until `articleToAdAccount.length > 0`.
  - **`visibleAccounts`** — Snap accounts filtered by `activeProviderIdsFromArticles` via `adAccountConfigs.feedProviderIds`; Meta accounts filtered by `provider.metaConfig.allowedAdAccountIds` of active providers. Sorted by minimum provider index; visible once any article is connected.
  - **`visiblePresets`** — filtered by `activeProviderIdsFromArticles` and sorted by provider index. Returns `[]` (nodes hidden) when `canSelectPresets` is false (no `articleToAdAccount` edge exists yet). Legacy presets with an empty `feedProviderId` no longer bypass the platform check unconditionally — they're shown only if *some* active provider actually has that preset's platform (`trafficSource === "facebook" ? "meta" : "snap"`) toggled on, same gate every other preset gets.
  - **Dark mode** — `<ReactFlow>` is rendered with `colorMode="dark"` and inline `style={{ background: "#1f2937" }}`; the `<Background>` component uses `color="#374151"` for the dot grid. Permanent dark mode is enforced via Tailwind `darkMode: 'class'` and `<html class="dark">`; all wizard components have `dark:` variants alongside their light classes.

- **synthesizeCampaign():** `lib/synthesize-campaign.ts` converts one `CampaignBuildItem` + resolved `(provider, article, preset, assets[])` into the `{campaigns[], adSquads[], creatives[]}` shape the orchestrator expects. One campaign + one ad squad are created. **Catalogue (Collection Ads) path:** when `preset.isCatalogue` is true, the function validates the preset has both `catalogId` and `productSetId` (throws otherwise), sets `campaign.catalogId`, and adds `isCatalogue: true` + `productSetId` + `dynamicTemplateId` onto each creative — otherwise it follows the SAME path as a regular ad (hero Silo asset + `buildUrlTemplate()` URL). Catalogue ads are NOT media-free; they need a hero image/video and a tracking URL just like normal ads. **Regular path:** `creatives[]` has one entry per asset (all share the same `adSquadId`); when multiple assets are passed, creative names are suffixed `[1]`, `[2]`, etc. It calls `buildUrlTemplate()` which resolves static URL macros now (`{{article.name}}`, `{{article.query}}`, `{{creative.headline}}`, `{{creative.rac}}`, `{{organization_id}}`), passing each resolved value through `encodeURIComponent` so spaces and special chars are safe. Any remaining `{{...}}` that aren't `{{campaign.id}}`, `{{adset.id}}`, `{{ad.id}}`, or `{{channel.id}}` are stripped (replaced with `""`) — Snapchat rejects both literal and percent-encoded unknown macros (E2712). The three Snapchat native macros and `{{channel.id}}` are left untouched — Snapchat substitutes the native ones at click time; the orchestrator resolves `{{channel.id}}`. If a parameter has `encode: true`, `encodeURIComponent` is applied to each segment of the value split on `{{channel.id}}`, then the segments are rejoined with the literal macro. This preserves `{{channel.id}}` through encoding so the orchestrator can resolve it after synthesis — previously the entire value was encoded, turning `{{channel.id}}` into `%7B%7Bchannel.id%7D%7D` which the orchestrator's regex never matched (CR-1 fix). `buildUrlTemplate()` returns `""` when parameters are present but the base URL is absent — prevents malformed `?key=value` strings with no host from reaching Snapchat.

- **Submission orchestrator:** `lib/submission-orchestrator.ts` runs **five stages** in sequence:
  1. **uploadMedia** — creatives upload with concurrency capped at 2 (Snapchat returns E3002 on 3+ simultaneous uploads to the same ad account). Catalogue (Collection Ad) creatives upload a hero image/video here just like regular creatives — there is no upload skip.
  2. **Channel assignment** — if `provider.channelConfig.type === "provider-supplied"`, calls `POST /api/feed-providers/channels/assign`; after assignment, `{{channel.id}}` in all campaign/squad/creative **names** is always replaced regardless of provider channel type (with the assigned ID, or `""` if none) — prevents literal `{{channel.id}}` from reaching Snapchat (E1001) even when a naming template uses the macro with a non-provider-supplied provider. URL `{{channel.id}}` is separately resolved in the URL macro step below
  3. **campaigns** — create campaigns in Snapchat
  4. **adSquads** — create ad squads in Snapchat. `placement_v2` is sent as `{ config: "AUTOMATIC" }` **only when `sq.smartPlacement` is true** (the preset's opt-in Smart-placement toggle) — which gives Snapchat auto-optimized placement but LOCKS the squad against API edits (E2025); otherwise `placement_v2` is omitted (Snapchat default placement, resolved `"SNAP_ADS"`, fully editable in-app). See the `placement_v2` PROVEN behaviour note under Snapchat API Field Notes. **Catalogue (Collection) squads:** `product_properties: { product_set_id }` is required on the ad squad AND must match the creative's `dynamic_render_properties.product_set_id` (E2840 if missing or mismatched). Do NOT send `catalog_vertical` or `child_ad_type` (E1001). `pixel_id` and `conversion_window` ARE sent (catalogue uses PIXEL_PURCHASE + SWIPE_7DAY, same rule as regular squads). The campaign MUST declare `product_properties: { catalog_id }` so Snapchat can validate the squad's product_set_id against the catalog (E2973 "Invalid catalog for dynamic product ads" if campaign lacks catalog_id).
  5. **creatives** — create creatives; **ads** — create ads. **Catalogue (Collection Ads):** before building creative payloads, for each catalogue creative the orchestrator creates 4 creative elements (`POST /api/snapchat/creative-elements`, type BUTTON / WEB_VIEW / DYNAMIC) then 1 interaction zone (`POST /api/snapchat/interaction-zones`, headline "MORE", render_type DYNAMIC) and stores `creativeId → interaction_zone_id` in `izMap`. Creatives whose zone fails are dropped (`buildableCreatives` filter) with a "Collection setup failed" error. The COLLECTION creative payload uses `type: "COLLECTION"`, `render_type: "STATIC"`, the uploaded `top_snap_media_id` (hero), `dynamic_render_properties: { product_set_id, dynamic_template_id? }`, and `collection_properties: { interaction_zone_id, default_fallback_interaction_type: "WEB_VIEW", web_view_properties: { url } }`. The ad payload uses `type: "COLLECTION"`.
  Each stage's results are tracked individually. `pacing_type` is hardcoded to `"STANDARD"`. The orchestrator accepts an optional `provider?: FeedProvider` parameter (6th arg) for channel assignment.

If org-scoped URL params are needed going forward, put the literal ID directly into a URL Parameters value instead.
