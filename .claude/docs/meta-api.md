# Meta (Facebook) Behaviour Notes

Hard-won Meta Graph API behaviour. Payload spec compliance lives here; Snapchat's equivalent is snapchat-api.md.

- **Meta preset bidding + pixel (confirmed against a live campaign via the Meta Ads MCP connector, and later against this account's live ad sets via GET /api/meta/adsets once that connector was disconnected):** `MetaAdSetPresetData.bidStrategy?: MetaBidStrategy` (`"LOWEST_COST_WITHOUT_CAP" | "COST_CAP" | "LOWEST_COST_WITH_MIN_ROAS"` — `LOWEST_COST_WITH_BID_CAP` exists on Meta's side but isn't offered in this app) + `bidAmountCents?` (Cost Cap target, only when `bidStrategy === "COST_CAP"`) + `roasFloor?` (ROAS floor ratio, e.g. `0.9` = 90%, NOT cents — sent as `bid_constraints.roas_average_floor` = `roasFloor * 10000`, only when `bidStrategy === "LOWEST_COST_WITH_MIN_ROAS"`; **not** `bid_amount` — see below). `PresetForm`'s "Bidding Strategy" select offers exactly two choices — "Maximize number of conversions" (`optimizationGoal: "OFFSITE_CONVERSIONS"`, optional Cost per Result Goal USD → `COST_CAP`; leave empty for `LOWEST_COST_WITHOUT_CAP`) / "Maximize value of conversions" (`optimizationGoal: "VALUE"`, optional ROAS Goal → `bid_constraints.roas_average_floor`). **"Maximize value of conversions" always forces `bidStrategy: "LOWEST_COST_WITH_MIN_ROAS"`, with or without a ROAS goal** — Meta rejects the default `LOWEST_COST_WITHOUT_CAP` paired with `optimization_goal: "VALUE"` (`"Bid Strategy Doesn't Support Value Optimization"`, error_subcode 1885324, confirmed live 2026-07-15). **The ROAS floor field name took three attempts to get right**: two attempts sent it through `bid_amount` (at `*1000`, then `*10000` scale) and both failed with the identical error; a live GET /api/meta/adsets check with `bid_constraints` added to the fields list showed the reference "boiler" campaign's 0.9 ROAS goal is actually stored as `bid_constraints: {"roas_average_floor":9000}` — a completely different field, not just a scale issue. Daily Budget (and the old separate Bid Amount field, now folded into the Cost per Result Goal input) take whole USD dollars in the UI — converted via `Math.round(x * 100)` once at submit; nothing downstream of the form changed, cents were already expected at the wire level. Meta's Pixel dropdown now sources `loadMetaPixels()` (was incorrectly sharing Snap's `pixelOptions` regardless of traffic source). **Editing an existing Meta preset bug fix:** `PresetForm`'s RHF `defaultValues` used to key off `sq0` (`preset.adSquads[0]`), which is always `[]` for Meta presets — editing a saved Meta preset silently reset Preset Name/Pixel/Status/Geo to blank/"new" defaults. Now keyed off `preset` directly with per-field fallback to `existingMetaAdSet` for Meta-specific values.
- **Pick a test ad account from the FEED PROVIDER config, never from the account list or from an example in these docs.** `/api/meta/ad-accounts` returns ~33 accounts; only the ones in some provider's `metaConfig.allowedAdAccountIds` are real launch targets (currently exactly two: `act_3683333958469415` → Predicto, divisor 100; `act_1549356156312143` → Vizymo, divisor 1). Query `user_metadata` key `br_feed_providers` and use that provider's own `allowedPageIds` for the page, which is the pairing the launcher itself uses via `pickBestPage()`. Cross-check `br_ad_accounts_v1`: an account with `hidden: true` and `feedProviderIds: []` is explicitly out of the pipeline and the dashboard filters it out.
  - **Do not select an account by name-matching a debugging anecdote in these docs** — done on 2026-08-04, picking `act_303868360771822` ("Amphy") with page "Margin Room" because both names appear in the Instagram-identity narrative below. That account is `hidden: true` with no provider, so every ad creation failed with `No Payment Method` (error_subcode 1359188) and a campaign/ad set/3 creatives were created in an account outside the pipeline before being deleted. The failure looked like a code bug and was purely a bad account choice. **`No Payment Method` on a test launch means you picked an unfunded account, not that anything is broken** — confirm the account has recent spend in `meta_ad_set_stats` before concluding otherwise.
- **Debugging Meta API errors without the Meta Ads MCP connector:** when that connector isn't connected, `GET /api/meta/adsets?adAccountId=act_<id>` (note the required `act_` prefix — `session.metaAllowedAdAccountIds` is always stored with it) is a live, authenticated way to inspect this account's real ad sets directly in the browser (already logged in) — compare a known-working campaign's fields against what this app is about to send, rather than guessing at Meta's undocumented field-pairing/encoding rules through repeated blind deploys. `getAdSetsByAccount`'s `fields=` query only returns what's explicitly listed — when a value visibly set in Ads Manager doesn't show up (e.g. a ROAS goal), the field name in the query is probably wrong, not the value absent; add candidate field names (e.g. `bid_constraints`) rather than concluding the account lacks the config. `GET /api/meta/ads?adId=<id>` (added 2026-07-16, same pattern, ownership-checked against `ad.account_id`) does the same for a single ad + its creative — used to confirm `instagram_user_id` and `degrees_of_freedom_spec` on a reference ad's creative.
- **Instagram identity on ad creatives:** Ads Manager's ad-level "Identity" section needs an Instagram actor even when no real IG professional account is connected to the Page — Meta falls back to the Page's own page-backed Instagram account (PBIA) when the "Use Facebook Page" option is used. Confirmed live 2026-07-16 via `GET /api/meta/ads` that a reference ad's creative carries `instagram_user_id` (the read-back name for the write field `instagram_actor_id`) even with no connected IG account. `meta-submission-orchestrator.ts` now resolves/creates each creative's page's PBIA via `getOrCreatePageBackedInstagramAccount()` (cached per page across creatives in one submission) and sets `instagram_actor_id` on the creative payload — through a new `GET /api/meta/media?pageId=` route, mirroring the existing `?videoId=` thumbnail lookup. This requires the `pages_read_engagement` scope, added to `buildMetaAuthUrl`'s scope string 2026-07-16 — **Meta connections made before this change must be reconnected once** or the PBIA lookup 403s and the ad is created with no Instagram identity (non-fatal — falls through silently, same pattern as the video thumbnail fetch). Adding a scope alone isn't enough to get it granted on reconnect: Facebook silently reuses a user's prior consent and skips the permission dialog for newly-added scopes unless `auth_type=rerequest` is set on the OAuth dialog URL — confirmed live 2026-07-16 (a user reconnected after the scope was added and still got the same 403, because `rerequest` wasn't set yet). `buildMetaAuthUrl` now always sets it. `GET /api/meta/media?pageId=` checks `instagram-actor-cache.ts`'s global, non-expiring Blob cache before calling Meta at all — a page's PBIA is resolved via the Graph API at most once ever (across all users/launches), not once per submission. The Page Backed Instagram Accounts edge (`/{pageId}/page_backed_instagram_accounts`) requires a **Page Access Token**, not the user's own token — `getOrCreatePageBackedInstagramAccount()` first fetches one via `GET /{pageId}?fields=access_token` (confirmed live 2026-07-16, error 190 "This method must be called with a Page Access Token" otherwise). **A resolved PBIA is only usable as `instagram_actor_id` by a specific ad account if that account actually has it listed in its own `GET /act_<id>/instagram_accounts`** — creating a PBIA does not make it globally usable, and (confirmed live 2026-07-16, corrected from an earlier wrong hypothesis) sharing a Business Manager with the page is **not** sufficient either: a real page ("Margin Room") owned by the same business as the ad account ("Amphy Performance", verified via a Business Settings screenshot) still 400'd ("Param instagram_actor_id must be a valid Instagram account id") because the PBIA was absent from both the ad account's `/instagram_accounts` AND the business-level `/{businessId}/instagram_accounts` — i.e. it was never actually connected/registered anywhere Meta recognizes, despite matching page-business ownership; this appears to require a manual step in Meta Business Settings, not something fixable via the API alone. `GET /api/meta/media?pageId=&adAccountId=` now checks the resolved PBIA against that specific ad account's own `/instagram_accounts` list (`isInstagramActorUsableByAdAccount()` in `business-pages.ts`) before returning it, falling through to no Instagram identity (same non-fatal path as a failed/missing PBIA) when it isn't usable there — the orchestrator passes `adAccountId` on this call for exactly this check.

- **"Flexible" ad format + Advantage+ creative optimizations:** the "Format" radio showing **Flexible** in Ads Manager is driven by `creative_asset_groups_spec` — a field on the **AD node itself** (sibling to `creative`), NOT on the creative and NOT on the ad set (both wrongly suspected and ruled out earlier: `is_dynamic_creative`+`asset_feed_spec` on the creative produces a "Dynamic creative"/"Single image or video" label instead, and `creative_asset_groups_spec` 400s as a nonexisting field on both the creative and the ad set). Confirmed live 2026-07-20 by capturing Ads Manager's own internal Relay preloader payload (BigPipe stream, operation `adp_AdsManagerLiveDataAdgroupQueryPreloadingConfigNoSpecsQueryRelayPreloader`) for a real reference ad (`120251719284310745`) — the literal string `"Flexible"` never appears in any public Graph API response or GraphQL body; the label is computed client-side by Ads Manager's frontend from the presence of this field. Shape: `{ origins: ["CAG"], groups: [{ call_to_action, images?: [{hash}], videos?: [{video_id, thumbnail_url?}] }] }` — `group_uuid` is server-assigned, don't send it. Verified live via the `meta-debug` test-launch tool: creating a plain single-image ad with this field added (reusing the same image already used by the ad's own `object_story_spec`) made the ad show "Flexible" in Ads Manager — a single asset in a single group is enough, no multi-asset restructuring needed. `meta-submission-orchestrator.ts` sets this on every ad unconditionally, reusing that ad's own `media.imageHash`/`media.videoId` (+ `videoThumbnailUrl` for video) for single-item creative groups. For 2+ item creative groups (multiple media added to the same wizard "creative group" card), the orchestrator instead bundles every item's image/video into ONE ad's `creative_asset_groups_spec.groups[0]` — see the `meta-submission-orchestrator.ts` Project Structure entry above; this is what makes a Meta "Flexible" ad actually flex across several real assets instead of just being a single-asset ad wearing the Flexible label. Separately, `degrees_of_freedom_spec.creative_features_spec` (still required, unrelated to the label above) drives the **Advantage+ creative optimizations** toggle: enrolling `advantage_plus_creative`, `inline_comment`, `product_extensions`, `site_extensions`, `text_optimizations` (all `OPT_IN`), plus `video_auto_crop` (video only — unconfirmed whether Meta accepts it on an image creative, so it's omitted there). `standard_enhancements` is deliberately **not** sent despite appearing in the reference ad's read-back: setting it on creative *creation* fails live with error_subcode 3858504 ("Creative should not include standard enhancements... has been deprecated. Please choose to set individual features instead") — GET still echoes it as a legacy aggregate view, but POST requires exactly the individual flags above instead. `buildAdvantagePlusCreativeFeatures(mediaType)` in `lib/meta/creative-features.ts` builds this spec; the orchestrator sets it on every creative unconditionally (no preset/UI toggle — matches the reference account's prevailing config, same pattern as the hardcoded `attribution_spec`). This helper had to live in its own dependency-free file rather than in `creatives.ts` — the orchestrator runs client-side (imported into `WizardShell.tsx`), and `creatives.ts` imports `metaFetch` from `client.ts`, which imports `lib/session.ts` (`next/headers`, server-only); importing that chain into a client component fails the build with "You're importing a component that needs next/headers." **Both fields require an explicit Zod schema entry in their respective API routes, same pattern as the campaign budget field above** — confirmed live 2026-07-20 when a real wizard-launched ad came back with `degrees_of_freedom_spec.creative_features_spec` fully `OPT_OUT` and no `creative_asset_groups_spec` at all, even though the orchestrator was building both correctly: `POST /api/meta/ads`'s Zod schema had no `creative_asset_groups_spec` key and `POST /api/meta/creatives`'s had no `degrees_of_freedom_spec` key, so both were silently stripped by Zod's default `.strip()` before ever reaching `createAd()`/`createAdCreative()` (which themselves just `JSON.stringify` whatever payload they're given — no filtering happens there). The earlier "confirmed live" verification only exercised the `meta-debug` test-launch route, which calls `createAd`/`createAdCreative` directly and bypasses these two API routes' schemas entirely — that gap is why the bug wasn't caught until a real wizard launch. Fixed by adding `creativeAssetGroupsSpecSchema`/`degreesOfFreedomSpecSchema` (mirroring `MetaCreativeAssetGroupsSpec`/`MetaDegreesOfFreedomSpec` in `types/meta.ts`) to both routes' `postSchema`. **Any future field added to an ad or creative payload in the orchestrator must also be added to that entity's API route Zod schema, or it will silently no-op exactly like this.** **Flexible ads render headline/primary text from `creative_asset_groups_spec`, NOT from `object_story_spec`** — confirmed live 2026-07-21: a launched ad had `object_story_spec.video_data.title`/`.message` both correctly populated (per-headline Meta copy — see the Articles section), yet Ads Manager's Flexible text editor showed "0 of 5" and the actual ad preview rendered no headline/primary text at all. `MetaCreativeAssetGroup` (`types/meta.ts`) now also carries `bodies?: Array<{text}>` / `titles?: Array<{text}>`; the orchestrator sets `titles: [{ text: metaHeadline || headline || "" }]` and `bodies: [{ text: metaPrimaryText || headline || "" }]` on every ad's `creative_asset_groups_spec.groups[0]` (both the single-item and 2+ item bundled paths) alongside `images`/`videos`. `object_story_spec`'s `name`/`title`/`message` are still set the same way and still required (they're the fallback Meta uses for non-Flexible contexts/API consumers), but for a Flexible-format ad they are NOT what actually displays — the asset-group `bodies`/`titles` are. Both new fields were added to `POST /api/meta/ads`'s `creativeAssetGroupsSpecSchema` in the same fix, per the Zod-schema rule directly above. **Ads Manager's manual "Ad creative" edit panel (Primary text/Headline "X of 5") does NOT reflect this** — confirmed live 2026-07-21: after the fix, the Ad Preview correctly rendered the headline/primary text, but that edit panel still showed "0 of 5". This panel is for variants typed by hand directly in Ads Manager; since our text arrives via the API under `origins: ["CAG"]`, Ads Manager's frontend doesn't round-trip it into that specific input list. This is cosmetic only — verify Flexible ad text via the **Ad Preview** pane, never via that edit panel's variant count.

- **Meta media pre-upload:** `uploadBlobToMeta()` (`lib/uploadMediaToMeta.ts`) is a single `POST /api/meta/media` call — no chunking or client-side polling needed, since that route already fetches the blob server-side (images) or hands the URL to Meta (video) and awaits `pollVideoStatus()` before responding. Returns `{ imageHash }` for images or `{ videoId }` for video. Used by `MetaUploadModal` for Silo pre-uploads.
- **Meta ad video processing status field:** the Ad Video node does NOT have a `processing_phase` field — confirmed live 2026-07-14 via `(#100) Tried accessing nonexisting field (processing_phase)`. Processing state is `status.video_status` (`"ready"` | `"processing"` | `"error"`). `pollVideoStatus()` (`lib/meta/creatives.ts`) polls `?fields=status`, returns on `"ready"`, throws immediately on `"error"` (no point retrying a failed video until timeout), and logs the raw response on its first poll attempt for fast diagnosis if the shape ever changes again.
- **Meta budget is always ABO (ad-set level), never CBO:** confirmed live 2026-07-14 via `error_subcode 1885621` ("Can't Set Ad Set and Campaign Budget — You can only set an ad set budget or a campaign budget."). The campaign payload built in `meta-submission-orchestrator.ts` must NEVER include `daily_budget`/`lifetime_budget` — budget is set only on the ad set (`MetaSynthesisResult.adSet.dailyBudgetCents`). `MetaSynthesisResult.campaign` has no budget field at all (removed from `synthesize-campaign.ts`). Do not reintroduce a campaign-level budget without also stripping it from the ad set — Meta accepts exactly one or the other, never both.
