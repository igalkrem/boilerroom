# Snapchat & Meta API Field Notes


### Graph API is pinned to v25.0 in ONE place (bumped 2026-07-30)
- `src/lib/meta/graph-version.ts` exports `GRAPH_VERSION` / `GRAPH_BASE` / `OAUTH_DIALOG`. It replaced five hardcodes across four files, which is how the app drifted onto v19.0 unnoticed. **A future bump is a one-line change to this file** — if you find a version string anywhere else, that is the bug.
- v25.0 is available until **29 Jul 2028**, the longest runway available. v26.0 shipped 29 Jul 2026 and is deliberately not used — a day-old version is where breaking changes land first.
- Verified against the live API with a real token before shipping: `me/adaccounts`, `{account}/adsets`, `/campaigns`, `/insights`, `/adcreatives` and `me/businesses` all return 200 on v25.0 with the same shapes as v19.0.
- **The Instagram identity field is `instagram_user_id` for both read AND write.** The old `instagram_actor_id` write name is unsupported from v22.0; the write-`actor`/read-`user` asymmetry documented for v19.0 no longer applies. Confirmed on v25.0 against real creatives: `instagram_user_id` populated, `instagram_actor_id` empty. Read `fields=` lists still request both so older objects keep resolving.
- **The create path has NOT been exercised against v25.0.** Only GETs were verified — confirming ad set/creative/ad creation needs a real wizard launch (`/api/meta/debug/test-launch` bypasses the Zod schemas the rename hinges on, so it does not count). Treat the first live Meta launch after this bump as the validation step.
- `instagram_story_id` / `effective_instagram_story_id` do not appear anywhere in the codebase, so the `source_instagram_media_id` / `effective_instagram_media_id` renames were no-ops.

### Historical: why the v19.0 bump was deferred (superseded 2026-07-30)
- v19.0's window closed **21 May 2026**. Calls still succeed (Meta sync ran 2026-07-30 06:48 with 2254 rows), because Meta serves the oldest supported version to an expired one. The risk is therefore **silent semantic drift**, not an outage — treat an unexplained Meta behaviour change as a candidate symptom.
- The bump is deliberately deferred because it cannot ship alone. `instagram_actor_id` is **unsupported from v22.0**, replaced by `instagram_user_id` for both write and read (the current write-`actor`/read-`user` asymmetry documented elsewhere in this file holds only for v19.0). Renaming it requires **four** coordinated edits: `src/types/meta.ts`, `meta-submission-orchestrator.ts` at **both** creative branches, and — critically — the `/api/meta/creatives` Zod schema. Miss the schema and the closed `z.object` strips the field, producing a creative with no Instagram identity at HTTP 200.
- Validate a bump with a **real launch through the wizard**. `/api/meta/debug/test-launch` calls `createCampaign`/`createAdSet`/`createAdCreative`/`createAd` directly and never touches the five Zod schemas, so "confirmed working" there proves nothing about the path that strips fields.
- `regional_regulated_categories` full enum: `TAIWAN_UNIVERSAL`, `SINGAPORE_UNIVERSAL`, `THAILAND_UNIVERSAL`, `BRAZIL_REGULATION`, plus a `*_FINSERV` family. `REGIONAL_DECLARATION_BY_COUNTRY` covers TW/SG/TH; only a custom country list reaches it, since the Worldwide path auto-excludes all three.
- **Never name a field on the write payload type without a matching Zod key.** `asset_feed_spec` sat on `MetaAdCreativePayload` with no schema key for exactly this reason and has been moved to the read type (`MetaAdCreative`), which is where `extractCreativeMedia()` consumes it. `standard_enhancements` has been deleted from `MetaCreativeFeaturesSpec` outright — Meta rejects it (`error_subcode 3858504`) and `creative_features_spec` is validated as a `z.record`, so a declared key would have had an unguarded path to the wire.
- **GET blindness:** Graph returns only fields named in `fields=`. `fetchImageUrls` read `entry.url` from an `/adimages` GET that requested nothing, which yields an empty map and a `502 no_media_downloaded` with nothing in the log; `getVideoThumbnailUrl` relied on the `/thumbnails` default set. Both now name their fields. Read types that `extend` a payload type over-promise for the same reason — `getAdSets` omits `bid_strategy`/`bid_constraints` (the two fields whose GET absence hid the original ROAS bug) and `getAdSetsByAccount` omits `targeting`/`billing_event`.

### Meta ads_volume (Ad Limits Per Page) — PROVEN behaviour (live probe, 2026-07-07)
- Endpoint: `GET /act_<AD_ACCOUNT_ID>/ads_volume?show_breakdown_by_actor=true` (Bearer). Works with the app's existing token/permissions.
- Each row: `{ actor_id (Facebook Page id), ads_running_or_in_review_count, current_account_ads_running_or_in_review_count, recommendations[] }`. `ads_running_or_in_review_count` is the **PAGE-LEVEL total** (identical value returned from every ad account that can advertise for the page); `current_account_ads_running_or_in_review_count` is that one account's slice. To build the per-page figure, call `ads_volume` for every Meta ad account and merge by `actor_id` (take the max — they agree). This matches the numbers on `business.facebook.com/latest/ad_limits`.
- **There is NO ad-limit field in the response.** The "250" shown in Business Manager is UI-only. `src/lib/meta/ad-volume.ts` exports `DEFAULT_PAGE_AD_LIMIT = 250`; the client computes `ads remaining = 250 − running`. The limit is fixed for every page (no per-page override). Do NOT add a limit field to the API mapper expecting Meta to return it.

- Campaign objective: `objective_v2_properties.objective_v2_type` is always `"SALES"` — hardcoded in the orchestrator and hidden from the UI.
- Campaign budget: only `daily_budget_micro` is supported (`spendCapType: "DAILY_BUDGET" | "NO_BUDGET"`). Minimum: $20 (20,000,000 micro) at the campaign level. Ad squads support both daily and lifetime — no $20 floor applies; the UI enforces only `> $0` (do NOT add a $20 minimum to ad squad budget inputs).
- `lifetime_spend_cap_micro` and `lifetime_budget_micro` are NOT sent on campaigns. `lifetime_budget_micro` is ad-squad only.
- `spend_cap_type` is an ad squad field only, not valid on campaigns.
- Ad squad `delivery_constraint` is required — `"DAILY_BUDGET"` or `"LIFETIME_BUDGET"`. `conversion_location` is NOT valid (E1001).
- Valid optimization goals (SALES + WEB): `PIXEL_PURCHASE`, `PIXEL_SIGNUP`, `PIXEL_ADD_TO_CART`, `PIXEL_PAGE_VIEW`, `LANDING_PAGE_VIEW`. Do not add goals from other objectives — they return E2844 with SALES objective.
- `conversion_window` is only sent for pixel-tracked goals (those starting with `PIXEL_`). `LANDING_PAGE_VIEW` is Snapchat-measured (no pixel event) and Snapchat rejects `conversion_window` for it with E1001 at the batch level. The orchestrator uses `sq.optimizationGoal.startsWith("PIXEL_") ? "SWIPE_7DAY" : undefined`.
- Ad squad pixel tracking: only `pixel_id` sent, always optional. `pixel_conversion_event` is NOT valid (E1001).
- Creative destination URL: `web_view_properties.url` (WEB_VIEW). **Both `APP_INSTALL` and `DEEP_LINK` have been removed** from `CreativeType`, `InteractionType` (wizard.ts), `INTERACTION_TYPE_MAP`/`AD_TYPE_MAP`, and the Zod schema (`creative.schema.ts`) — do not add either back. `APP_INSTALL` fell through to `SNAP_AD` with no `app_install_properties`; `DEEP_LINK` (removed 2026-07-30) sent only `deep_link_uri` while the API also requires `app_name` (max 30), `icon_media_id`, one of `ios_app_id`/`android_app_url`, and campaign `measurement_spec` — so it would have been rejected *after* the campaign and ad squads were already created. Neither is reachable from the business model: a deep link or app install carries no `channel_id`, so it earns no reconcilable feed revenue.
- **Two DEEP_LINK survivals that must not be "cleaned up":** (1) `SnapCreativeElementPayload.interaction_type: "WEB_VIEW" | "DEEP_LINK"` (`types/snapchat.ts`) is the Collection-ad *button element* — a different Snapchat concept that is in active use; removing it breaks Collection ads. (2) `deep_link_properties` remains on `SnapCreative` (the **response** type, not `SnapCreativePayload`) because the PATCH path in `api/snapchat/creatives/[id]` re-sends an existing creative's properties when updating its web view URL — a creative authored in Snap's Ads Manager can carry the field, and dropping it would silently strip it on edit.
- Ad destination URL: URL fields are NOT sent on the Ad payload — Creative only. Ad payload: `ad_squad_id`, `creative_id`, `name`, `type`, `status`.
- Ad `type` for WEB_VIEW creatives is `"REMOTE_WEBPAGE"`. `AD_TYPE_MAP`: `WEB_VIEW → REMOTE_WEBPAGE`, all others → `SNAP_AD`.
- Interaction type is hardcoded to WEB_VIEW. **`call_to_action` is valid on `WEB_VIEW` creatives.** Do NOT send `call_to_action` on `SNAP_AD` creatives (E2002). Not user-configurable — `submission-orchestrator.ts` always sends the literal `"MORE"` for non-`SNAP_AD` creatives (Meta creatives always get `"LEARN_MORE"` — see `meta-submission-orchestrator.ts`). There is no CTA picker anywhere in the app (preset form or canvas wizard).
- `headline` is optional on creatives (`SnapCreativePayload`). Do NOT send `headline: ""` — Snapchat defaults `brand_name` to `""` when omitted, and E2607 fires if both are the same value (including both empty). Orchestrator uses `cr.headline || undefined`.
- Batch error responses: errors in `sub_request_error_reason` (not `error_type`/`message`).
- Ad squad geo targeting: `targeting.geos` (NOT `geo_locations`) — `{ country_code: string }` with **lowercase** codes. Old presets with `geoCountryCode` (singular) are migrated on load.
- Ad squad device targeting: the app sends **only** `{ os_type, operation }` and never `device_type` — which is correct. Per the live ad-squads doc, `device_type` is `"MOBILE"` or `"TABLET"`, while `"WEB"` is an **`os_type`** value (`iOS`/`ANDROID`/`WEB`), so the earlier note here claiming `device_type: "MOBILE"|"WEB"` conflated the two fields. `buildDemographics()` maps a WEB device selection to `os_type: "WEB"`, and MOBILE with no OS to two INCLUDE entries (`iOS` + `ANDROID`), which OR together.
- Ad squad demographics: the gender key is **`gender`** — singular, bare string (`"MALE"`/`"FEMALE"`/`"OTHER"`), **not** `genders: [...]`. `min_age`/`max_age` are quoted integer strings (`"13"`–`"55"`), not numbers. Both confirmed against the targeting reference parameter table and the example-targeting-specs page 2026-07-30.
- Campaign vs ad-squad budget floors are different: campaign `daily_budget_micro` minimum is 20,000,000 ($20), ad-squad minimum is 5,000,000 ($5). `lifetime_spend_cap_micro` IS a valid campaign field per the docs — the app deliberately never sends it, which is a product choice rather than an API constraint.
- Ad squad demographic targeting: `min_age` and `max_age` are **plain integer strings** between `"13"` and `"55"`, not numbers and not `"55+"`. Sending numbers causes E1001; sending `"55+"` causes E2401 ("max_age value must be between 13 and 55"). The Snapchat UI labels the upper bound as "55+" but the API value is `"55"`. The `AGE_OPTIONS` constant in `PresetForm.tsx` stores `value: "55"` with `label: "55+"` to handle this divergence.
- **`placement_v2` and Dynamic Product Ads (DPA/Catalogue) — CHAT_FEED conflict:** Snapchat's official docs state that Dynamic Product Ads **prohibit CHAT_FEED** entirely. However, for PIXEL_PURCHASE optimization goal, CHAT_FEED is **mandatory** (enforced since Nov 27, 2025 — E21011 if missing). This creates an impossible constraint: no CUSTOM `placement_v2` config is valid for catalogue ad squads. AUTOMATIC would create the squad but permanently lock it against API updates (E2025). **The only safe path for catalogue squads is to omit `placement_v2` entirely** — same as regular squads.

- **`placement_v2` — AUTOMATIC config restriction:** When `config` is `"AUTOMATIC"`, no other properties (`platforms`, `snapchat_positions`) may be included in the `placement_v2` object — Snapchat rejects the payload if they are present.

- **`placement_v2` — INTERSTITIAL_SPOTLIGHT cannot stand alone:** Must always be combined with at least one other `snapchat_positions` value.

- **Catalogue (Dynamic Collection Ads) API fields** — confirmed from live campaign `625ce435-d6f3-42b1-b39d-d605df3f866f` and ad squad `35d2ad6a-3ae9-4874-b3e3-c401a6b92e00`. A catalogue ad is a **Collection Ad**: a static hero image/video on top + a row of 4 dynamic product tiles below it. It is NOT a media-free ad. Full creation chain:
  - **Campaign:** `product_properties: { catalog_id: string }` (required — Snapchat validates squad's product_set_id against this catalog; omitting causes E2973). Objective still `SALES`.
  - **Ad squad:** `product_properties: { product_set_id }` required (E2840 if missing) — must match creative's `dynamic_render_properties.product_set_id`. No `child_ad_type`, no `catalog_vertical` (E1001 — read-only fields Snapchat auto-sets). `pixel_id`, `optimization_goal: "PIXEL_PURCHASE"`, and `conversion_window: "SWIPE_7DAY"` ARE sent (same rule as regular pixel-tracked squads).
  - **Creative elements (×4):** `POST /adaccounts/{id}/creative_elements`, body `{ creative_elements: [...] }`, each element `{ name, type: "BUTTON", interaction_type: "WEB_VIEW", render_type: "DYNAMIC" }`. These are the product-tile placeholders.
  - **Interaction zone (×1):** `POST /adaccounts/{id}/interaction_zones`, body `{ interaction_zones: [{ name, headline: "MORE", creative_element_ids: [4 ids], render_type: "DYNAMIC" }] }`. Groups the 4 elements.
  - **Creative:** `type: "COLLECTION"`, `render_type: "STATIC"`, `top_snap_media_id` (the hero — REQUIRED), `dynamic_render_properties: { product_set_id, dynamic_template_id? }`, `collection_properties: { interaction_zone_id, default_fallback_interaction_type: "WEB_VIEW", web_view_properties: { url } }`, `profile_properties: { profile_id }`, `headline`. `call_to_action` is omitted (the tile CTA is the interaction zone's `headline: "MORE"`); the live creative had no `call_to_action`. `dynamic_template_id` optional (Snapchat account default if absent).
  - **Ad:** `type: "COLLECTION"`, `render_type: "DYNAMIC"` (required — Snapchat defaults to STATIC and rejects with E2841 if absent).

- **`placement_v2` — PROVEN behaviour (live probe, ad account `082c59b3…`, 2026-07-06 — see `snapchat-placement-debugger` agent + `/api/debug/placement-probe`):**
  - **Omit `placement_v2` (default):** squad creates and its resolved legacy `placement` = `"SNAP_ADS"` (a fixed default, NOT auto-optimized "Smart"). Squad stays **fully editable** via PUT. This is the default path.
  - **`{ config: "AUTOMATIC" }` (Smart placement) on POST:** squad **creates successfully** and its resolved legacy `placement` = `"UNSUPPORTED"`. A PUT that omits `placement_v2` returns `E2025: "Update is not supported for this entity : [AdSquad was created with placement v2, please update the placement in Ads Manager]"`. **That is NOT a lock — see the E2025 entry below. The squad is fully editable when `placement_v2` is echoed back.**
  - **`{ config: "CONTENT" }`:** **rejected at create** — `E39400: "Placement config must be AUTOMATIC or CUSTOM : [got: UNRECOGNIZED]"`. CONTENT is not a valid config value; never offer it in the UI.
  - **`{ config: "CUSTOM", snapchat_positions: [...] }`:** requires `CHAT_FEED` in the positions or Snapchat returns `E21011: "For this optimization goal, you must have chat feed placement selected"` (fired even for `LANDING_PAGE_VIEW`). CUSTOM is still `placement_v2`, so it resolves to `placement: "UNSUPPORTED"` and needs the same echo-on-PUT treatment as AUTOMATIC.
  - **Editing placements in Snapchat Ads Manager also flips a squad to `placement_v2`** (confirmed 2026-07-06 via the `adsmanager-recheck` probe mode): a squad created without `placement_v2` (resolved `"SNAP_ADS"`) that then has its placements changed in Ads Manager becomes resolved `"UNSUPPORTED"` and returns E2025 on the next PUT that omits `placement_v2`. Such a squad is editable again via the echo, exactly like an AUTOMATIC one — no Ads Manager round-trip needed.
  - **E2025 IS NOT A LOCK — it means `placement_v2` was omitted from the PUT body (confirmed live 2026-08-05).** Snapchat reads a missing `placement_v2` as an attempt to *clear* the field and refuses. Echo the squad's own `placement_v2` back and **budget, bid and status all apply normally**. Proven on one squad seconds apart: PUT with `placement_v2` echoed → `SUCCESS`, `daily_budget_micro` 5,000,000 → 6,000,000 confirmed by a fresh GET; the identical PUT with only that field removed → E2025, value unchanged. Re-confirmed for `bid_micro` (1,000,000 → 1,500,000) and `status` (PAUSED → ACTIVE) on a squad created with `LOWEST_COST_WITH_MAX_BID` so `bid_micro` was a real value rather than AUTO_BID's 0. Request IDs and full payloads are in the support case sent to Snapchat (`~/Desktop/snapchat-support-reply.md`).
  - **Reading `placement_v2` requires `?return_placement_v2=true` — a plain GET never returns it.** This parameter is not in the public docs; it came from Snapchat TAS via support on 2026-08-05 and is the reason this went undiagnosed for a month. `getAdSquadPlacementV2()` (`src/lib/snapchat/adsquads.ts`) wraps the flagged GET. **The earlier combination sweep's "echo `placement_v2` back" arm never actually ran**: its GET lacked the flag, so `placement_v2` was `null` in all 15 records and the arm silently degraded into the no-echo arm. Its conclusion that no Smart-AND-editable combination exists was drawn from a test that never executed.
  - **The echo MUST be conditional on the squad actually being placement_v2-based.** For a squad created **without** `placement_v2`, the flagged GET does not return "no placement" — it returns a **SYNTHESISED** object (confirmed live 2026-08-05): `{"config":"CUSTOM","platforms":["SNAPCHAT"],"snapchat_positions":["INTERSTITIAL_USER","INTERSTITIAL_CONTENT","INSTREAM"]}`. That is Snapchat's `placement_v2` translation of the legacy `SNAP_ADS` default, **not** the squad's own config. Echoing it back on a PIXEL_PURCHASE squad fails with E21011 (CHAT_FEED required), and anywhere it succeeded it would convert a fully editable squad into a locked CUSTOM-placement one. **A blanket "always echo" is unshippable.**
  - **Order in `updateAdSquad()` is load-bearing:** (1) detect the lock with the **PLAIN** GET's legacy `placement === "UNSUPPORTED"` — the flagged GET omits `placement` entirely, so it cannot serve this; (2) only for a locked squad, fetch `placement_v2` via the flagged GET and set it on the merged PUT body. `placement_v2` stays out of `ADSQUAD_PUT_ALLOWED_FIELDS` — not because it must never be sent, but because `stripForPut` operates on a plain-GET squad that never carries it. Verified on **both** squad types before shipping: an ordinary squad edits budget/bid/status with no echo and remains `SNAP_ADS`; a Smart squad edits all three with the echo and remains `UNSUPPORTED`.
  - **The campaign-status redirect is gone** (removed 2026-08-05 along with `updateCampaignStatus()` in `campaigns.ts`). It existed only to recover pause/activate on squads believed permanently locked, and carried three guards — refusing ACTIVE when the squad's own status was PAUSED, and refusing any toggle when the campaign held sibling squads, because campaign status is not squad-scoped. All obsolete now the squad itself is editable. **Do not reintroduce it**; campaign-level `daily_budget_micro` in particular is a spend *ceiling* layered on top of the squad's own budget, never a substitute (verified in Ads Manager 2026-07-27 after a read-back test wrongly suggested otherwise).
  - **Both placement_v2 shapes that exist in the wild are confirmed editable via the echo (surveyed + tested 2026-08-05).** A read-only sweep of all 21 accessible ad accounts found **823 of 1,258 ad squads carrying `placement === "UNSUPPORTED"`** — i.e. ~65% of the entire live inventory was affected by this, not just newly-created squads. Sampling 40 of them found exactly two shapes, and **every one returned a real `placement_v2` to echo** (none came back empty):
    - `{config:"AUTOMATIC"}` — 33/40. The Smart-placement opt-in path.
    - `{config:"CUSTOM", platforms:["SNAPCHAT"], snapchat_positions:[INTERSTITIAL_USER, INTERSTITIAL_CONTENT, INTERSTITIAL_SPOTLIGHT, INSTREAM, PUBLIC_STORIES_INSTREAM, FEED, CHAT_FEED]}` — 7/40. What an Ads Manager placement edit leaves behind.
    The CUSTOM shape was reproduced verbatim on a throwaway squad and put through the same echo-vs-no-echo comparison: budget, bid and status **all applied with the echo and all returned E2025 without it**, and the 7 `snapchat_positions` **survived every edit unchanged** — the echo restores placement rather than rewriting it. So the fix covers pre-existing campaigns, including ones locked by an Ads Manager edit, with no migration or re-launch needed. `survey-existing.mjs` / `verify-custom-shape.mjs` in the pv2 lab reproduce both checks (read-only and throwaway respectively).
  - **The shipped code path is verified end to end, not just the algorithm.** `make-fixtures.mjs` leaves a locked and an ordinary throwaway squad alive; driving the real `PATCH /api/snapchat/adsquads` against them (local dev server + `/api/auth/dev-login` session) moved the Smart squad's budget 5M→7M, bid 1M→2M and status PAUSED→ACTIVE while it stayed `UNSUPPORTED`, and moved the ordinary squad's budget while it stayed `SNAP_ADS`. Every value confirmed by a fresh GET — never by the HTTP 200, which Snapchat returns even when the batch item carries an error.
  - **Catalogue (DPA/Collection) squads are a SEPARATE, still-unfixed problem — do not confuse the two.** A catalogue squad fails every budget/bid/status edit with Snapchat's own server-side `E4001: "Failed to copy over @DaoImmutable property productProperties.catalogVertical"`, **with or without the placement_v2 echo** (confirmed live 2026-08-05 on a real ACTIVE DPA campaign: both variants returned the identical error, so E4001 is hit before placement is ever evaluated). The placement fix neither helps nor hurts here. In the account surveyed, **33 of 81 locked squads were catalogue** — so roughly 40% of "locked" squads in a DPA-heavy account are blocked by this instead. Distinguish them by `product_properties` being present on the squad (`{product_set_id, catalog_vertical}`), not by placement.
    **Transport gotcha:** catalogue squads return this as **HTTP 500**, not the usual HTTP 200 + `sub_request_status: "ERROR"`. `snapFetch` therefore throws, which for a long time made `updateAdSquad`'s `catalogVertical` special-case unreachable — it sat inside the 200-with-batch-error branch, so users got the opaque `snapchat_request_failed` instead of the real reason. Fixed 2026-08-05 by also catching the thrown error and matching on `catalogVertical` there. **Any future error-shape special-case in this function must cover both transports.**
  - **The Smart-placement trade-off no longer exists.** `smartPlacement` on a preset is now a free choice: the orchestrator still sends `placement_v2: { config: "AUTOMATIC" }` only when the preset opts in, but opting in no longer costs in-app editing. `PresetForm`'s amber "locked by Snapchat — manage in Ads Manager" warning was replaced accordingly. `PerformanceTable.friendlyPatchError`'s E2025 branch is now an unexpected-error path (the echo failed), not an explanation of normal behaviour.

- Fields intentionally omitted from payloads: `frequency_cap_max_impressions`, `frequency_cap_time_period`, `shareable`. Hardcoded: `pacing_type` (`"STANDARD"`). `profile_properties: { profile_id: string }` is required on creatives (E2652 if absent, E2006 if null) — orchestrator auto-fetches via `GET /api/snapchat/profiles`; returns early with errors if unresolvable.
- Batch API response order is not guaranteed — orchestrator matches by `name` with positional-index fallback (`find(r => r.name === x) ?? results[i]`). Both layers required.
- **PUT `/adsquads/{id}` silently no-ops on read-only fields:** Snapchat returns HTTP 200 with `sub_request_status: "ERROR"` (and the unchanged adsquad echoed back) when the body contains server-computed fields like `created_at`, `updated_at`, `delivery_status`, `effective_status`, `forced_view_eligibility`, `auto_bid`, `ranking_score`. `updateAdSquad` strips to a whitelist (`ADSQUAD_PUT_ALLOWED_FIELDS` = id, campaign_id, name, type, status, targeting, delivery_constraint, billing_event, optimization_goal, bid_strategy, bid_micro, daily_budget_micro, lifetime_budget_micro, conversion_window, pacing_type, start_time, end_time, pixel_id) before PUT, and inspects `sub_request_status` on the response — throws with `error_type: message` (or `sub_request_error_reason`) when not SUCCESS. Without both checks, the PATCH route returns 200 to the client while Snapchat never applied anything. **`placement_v2` is intentionally excluded** — sending it back causes E2025 ("Update is not supported for this entity") on squads created with placement_v2. **`bid_micro: null` or `bid_micro: 0`** is excluded — auto-bid squads return 0 from the API and sending it back triggers E2771 ("Bid is required on ad squad").
- **Stats API (`/adsquads/{id}/stats`):** `granularity=DAY` returns `timeseries_stats[0].timeseries_stat.timeseries[]` — NOT `total_stats` (which is only used for `granularity=TOTAL`). The `spend` field in `timeseries_stats` is already in **micro-dollars** (do NOT multiply by 1,000,000). Times must be at midnight in the ad account's actual IANA timezone (passed from `SnapAdAccount.timezone` — e.g. `"Asia/Jerusalem"`, `"America/Los_Angeles"`). Offset is computed dynamically via `Intl.DateTimeFormat` with `timeZoneName: "shortOffset"` — handles half-hour offsets and DST automatically. `end_time` must be midnight of the day AFTER the last desired date (exclusive). `ts.start_time` in the response is UTC — convert to local date via `Intl.DateTimeFormat("en-CA", { timeZone })` (not `slice(0,10)`) to avoid off-by-one for UTC+ zones. Sync route accepts a `force: boolean` param (default `false`) to bypass the 1-hour re-fetch throttle; date picker changes and manual refresh always pass `force: true`; historical window syncs pass the same `force` value as the main range (not hardcoded `false`). Country breakdown (`report_dimension=country`) is not used — stats are totals only. Valid `fields`: `impressions`, `swipes`, `spend`, `video_views`, `conversion_purchases`, `conversion_purchases_value`. **The value field is `conversion_purchases_value` (plural "purchases") — NOT `conversion_purchase_value` (singular).** Using the singular name causes E1004 "Unknown Field" for all pixel-purchase squads. `conversion_purchases_value` is in micro-dollars (same unit as `spend`); stored in DB as `conversion_purchase_value` BIGINT (internal name) and divided by 1,000,000 in the combined/drilldown response mappers as `snap_purchase_value_usd`. `getAdSquadStats` uses a 3-tier fallback: (1) all six fields; (2) on E1004 for `conversion_purchases_value`, retry with base + `conversion_purchases`; (3) on another E1004, retry with base fields only — so spend/impressions are never lost even for non-conversion squads. `conversion_purchases` is a count stored as `snap_results`. `snap_cost_per_result` is computed client-side as `spend_usd / snap_results`.
