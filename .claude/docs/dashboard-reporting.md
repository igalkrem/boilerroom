# Performance Dashboard & Reporting Pipeline

Metrics, attribution joins, the ROAS divisor, and the two coexisting conversion-value scales.

- **Performance dashboard:** `/dashboard/performance` — **default landing page**. Loads from DB immediately on mount; cron at :15/:46 keeps DB fresh. Next to `DateRangePicker`: **‹/› prev/next-day buttons** shift both `startDate` and `endDate` by one day (preserves range length, calls the same `handleDateChange`); the next-day button is capped/disabled once `endDate` reaches today so the range can never move into tomorrow. Also a **"Clear filters (N)"** button, disabled at N=0 — `PerformanceTable` is wrapped in `forwardRef` exposing a `clearAllFilters` imperative handle (`PerformanceTableHandle`) and reports its `activeFilterCount` up via `onActiveFilterCountChange`, so the page-level button can clear the table's internal filter state without lifting it. The page has no subtitle under the "Performance" heading (removed 2026-07-29). **SyncStatusBar** sits on the same toolbar row as `DateRangePicker`/prev-next/Clear filters, aligned to the right via `justify-between` on the shared row (moved 2026-07-29 — previously its own row above the date picker); shows per-feed status: Visymo (feed dot + snap accounts dot) and Predicto — green when snap was synced after the feed, amber when feed updated more recently than snap, **red when feed is >75 min old** (means a cron cycle was missed or the API call failed silently). A subtle icon-only Force Refresh button (right end of the bar) is an escape hatch for manual override. **Load flow:** `loadFromDb` (reads DB only, fast) runs on mount; `syncAndReload` calls `loadFromDb` first (instant data), then syncs all APIs, then reloads again; on mount, if 0 rows returned, `syncAndReload` auto-seeds; if rows exist but any feed is >75 min stale, `syncAndReload` auto-heals in background (cron-miss safety net — triggered by checking `/api/reporting/sync-status` after the initial DB load); date-range changes call `loadFromDb` first and only trigger `syncAndReload` if 0 rows found (avoids unnecessary API calls when DB already has the data); `syncRefreshTrigger` increments after each sync completes to tell `SyncStatusBar` to re-fetch status. **Sync optimization:** Visymo re-fetched only after :15 of each hour; Predicto/Predicto FB only after :46 — `shouldSkipFeed()` in sync-logic gates all three. `force=true` (dashboard Force Refresh, and cron which always passes force=true) returns `false` immediately, bypassing BOTH the permanent "< yesterday" historical block AND the per-hour window check — matching how `shouldSkip()` already treats `force` for Snapchat/Meta per-account stats (`!force && shouldSkip(...)`). This means clicking Force Refresh always re-fetches live feed data regardless of when it last synced, consistent with the button's tooltip ("re-fetches all sources regardless of cache"); non-forced callers (page mount, date change with existing rows) still respect the once-per-window throttle. Cron passing `force=true` on every tick doesn't add extra load since cron's own schedule is fixed at exactly :15/:46 (twice/hour) regardless. Snapchat syncs are source-coupled: Visymo accounts at :15, Predicto accounts at :46. **Squad details** (Status/Budget/Bid) fetched via `getAdSquadsByAccount` — single `GET /adaccounts/{id}/adsquads` call per account (replaced the old per-campaign N+1 fan-out that caused 40–50s load times on large accounts). **Account detection:** `loadAdAccountConfigs()` drives the hidden filter for BOTH platforms — `activeAccounts` (Snap) and `activeMetaAccounts` (Meta) each drop accounts whose config has `hidden: true`. Fallback to "show all" ONLY when `adAccountConfigs.length === 0` (fresh user, nothing configured); once any config exists the hidden flag is respected exactly, including the all-hidden case (show nothing). Every Meta load path (`loadFromDb`, `loadLast30Days`, `syncAndReload`, `loadSquadDetails`) uses `activeMetaAccounts`, and the mount + squad-detail effects fire when either platform has active accounts (so hiding all Snap while keeping Meta active still loads). **Multi-account:** `runWithConcurrency` (page-local helper, `ACCOUNT_SYNC_CONCURRENCY = 3`) caps how many accounts sync at once per platform — each account's own main+historical calls still run in parallel, but only 3 accounts run concurrently. This exists because Snapchat's rate limiter (`rate-limiter.ts`) is per-serverless-invocation, not global: firing every account's sync request at once (one invocation per account) multiplies past Snapchat's real per-app rate limit, causing genuine 429s whose retry backoff (up to 30s/call) previously pushed squad-heavy accounts' `/api/reporting/sync` calls past their timeout (confirmed via a live 504 in Vercel logs); `/api/reporting/sync` and `/api/reporting/meta-sync` `maxDuration` was also raised 120→300 as a safety margin. Squad detail loads (`loadSquadDetails`) still use plain `Promise.allSettled` per account; rows merged. **Historical ROI:** `syncAndReload` accepts `includeHistorical = true` (5th param). When `true`, it fires a parallel sync for `[startDate−3, startDate−1]` alongside the main range so the -1D/-2D/-3D ROI columns are populated; the historical sync passes the same `force` value as the main range — so Force Refresh (force=true) also unblocks old dates that would otherwise be permanently skipped by `shouldSkipFeed`'s `dateObj < yesterday` guard (Visymo/Predicto) and `shouldSkip`'s guard (Snapchat). When `false` (passed by `handleManualRefresh`), only the selected date range is synced — Force Refresh fetches exactly what is in the date picker, no more. Page then fetches an additional `combined` call for those 3 days and stores it in `historicalRows`; table computes -1D/-2D/-3D ROI per campaign using `dateMinus(startDate, N)` — relative to the selected range, not today. **Layout:** `KpiSummaryBar` (always visible, skeleton while loading) above `PerformanceTable`. KPI bar sums raw `CombinedRow[]` for grand totals (spend, revenue, ROI, profit, impressions, clicks, funnel clicks, CTR). **Table toolbar:** always-visible bar inside `PerformanceTable` with left side (N selected + Edit/Delete buttons when rows selected) and right side (search input, Filters button, "Ignored (N)" toggle, `ColumnSelector`, CSV download). `ColumnSelector` lives in the toolbar, not in `page.tsx` controls. **Bulk edit:** "Edit" button in toolbar toggles a collapsible card-based panel between toolbar and table headers. Cards: **Budget** and **Bid** each have a 3-tab mode selector — `$ Set` (absolute value, same as old behavior), `+/- $` (add or subtract a fixed dollar amount from each squad's current value), `+/- %` (multiply each squad's current value by `1 ± pct/100`); a green `+` / red `−` direction toggle appears for the two non-Set modes. Per-squad patch computation: for Set mode one patch object applies to all; for +/- modes the new value is computed inside the `Promise.allSettled` loop per squad from `squadDetails.get(squadId).daily_budget_micro` / `bid_micro`. **Status** card unchanged. `applyBulk(field)` validation is mode-aware (percentage or dollar amount must be > 0). `onSquadPatched` receives the per-squad computed patch for correct optimistic UI updates. **Ignore** card (added 2026-07-29) — a fourth card, no PATCH involved: `hideSelected()` bulk-adds all selected squad IDs straight into the same client-side `hiddenSquadIds`/`br_perf_hidden_squads` mechanism the single-campaign DrilldownModal "Ignore campaign" toggle already used, letting a multi-selection be hidden from the dashboard in one click instead of one row at a time. Panel hidden when no rows selected or Edit toggled off. **Filters:** funnel-icon "Filters" button (turns blue when active, shows count badge e.g. "Filters · 3") toggles a filter panel below the toolbar (coexists with the bulk-edit panel). Four filter types: (1) **Article** — multi-select dropdown from `boilerroom_articles_v1` localStorage; has a live search input at the top of the dropdown (auto-focused on open, cleared on close); OR logic; match = `article.slug` (space/hyphen/underscore-normalized) is substring of `ad_squad_name`; (2) **Feed Provider** — multi-select dropdown from `boilerroom_feed_providers_v1` localStorage; also has a live search input; OR logic; match = exact `feed_provider_id` from DB (sourced via LATERAL JOIN on `feed_provider_channels`; reliable for both Visymo and Predicto campaigns — do NOT match on `domain_name` or campaign name substring, which fail for channel-named campaigns); (3) **Status** — pill toggle buttons (Active / Paused); each pill toggles independently; green pill = Active, yellow = Paused; reads `squadDetails.get(ad_squad_id)?.status`, defaulting to `"ACTIVE"` when absent; independent of the always-on "PAUSED + zero impressions" auto-hide; (4) **Metric filters** — add/remove rows of `[metric ▼][op: > ≥ < ≤][value][×]`; AND logic; incomplete rows skipped. "Clear all" resets all filters. `FILTERABLE_METRICS` constant (module-level, 15 entries) defines filterable metric keys. **Columns:** `ColumnSelector` — 29 toggleable columns (raw + computed metrics: CPM, CPC, CTR, RPC, Revenue per Result, Fill Rate, CVR, Profit + 3 Snap conversion cols: Results/Cost per Result/Purchase Value); default visible set excludes lesser-used columns; new Snap cols are opt-in only. Column label notes: "Clicks" = Snap swipes, "Ad Clicks" = Visymo + Predicto combined `clicks`, "Funnel Clicks" = Visymo + Predicto combined `funnel_clicks`, "Requests" = Visymo `ad_requests` + Predicto `requests` (combined), "Feed Impressions" = Visymo `individual_ad_impressions` + Predicto `impressions` (combined). **Formatting:** ROI columns render as whole-number percentage pills via `roiHeatmap()` with heatmap background coloring (green ≥ 120%, orange 105–119%, red ≤ 105%, gray dash when null); CVR renders whole-number via `fmtPct0`; CTR keeps 2 decimal places (`fmtPct`). **Snap logo:** small yellow Snapchat ghost icon (`SnapchatLogo` inline SVG) shown left of every campaign name cell. **Table column order:** Checkbox | Name | Status toggle | Delivery badge | Budget | Bid | [metric columns]. **Computed metrics:** all calculated client-side in `PerformanceTable` `useMemo`. Formulas: RPC = `revenue / ad_clicks` (requires `funnel_clicks >= 10` to suppress noise on low-volume rows); Revenue per Result = `revenue / snap_results` (same `funnel_clicks >= 10` guard); Fill Rate = `funnel_impressions / snap_clicks` (as %); CVR = `funnel_clicks / swipes` (as %); CPR was removed. **Inline controls:** Budget and Bid cells have pencil-icon edit mode (click → input → Enter/blur saves via PATCH); Status toggle fires PATCH immediately. PATCH responses with `!res.ok` are parsed for `{message}` and surfaced in `inlineError`/`bulkError` so Snapchat rejections (e.g. read-only field errors) are visible. **Optimistic update:** on successful PATCH, `onSquadPatched(squadId, patch)` updates the parent's `squadDetails` map immediately so the new value sticks even if the follow-up `loadSquadDetails` reload is delayed/flaky. **Squad-detail load resilience:** `loadSquadDetails` retries each account up to 2× with 1s/2s backoff, checks `r.ok`, and merges per-account into existing state — failed accounts keep their previous squads instead of disappearing into `…` placeholders. A soft amber banner ("Could not load campaign settings for N accounts — refresh to retry") surfaces when retries exhaust. **Delivery badge:** `bg-green-100` pill showing Active/Paused derived from same `SquadDetail.status` field. **Drilldown:** clicking a campaign name opens `DrilldownModal`. The modal header has a "Columns" button (`ColumnSelector`, 26-metric set, `br_drilldown_cols` / `br_drilldown_cols_order` — independent of the main table's `br_perf_cols`) and an eye-slash "Ignore campaign" button for hiding/unhiding the campaign from the table. **Campaign filter:** search input in table toolbar; client-side substring filter on `ad_squad_name`. **Ignored campaigns:** the eye-slash "Ignore campaign" button lives in the `DrilldownModal` header (`isHidden` + `onToggleHide` props) — open a campaign's drilldown to hide/unhide it. Hidden squad IDs are persisted in `localStorage` under `br_perf_hidden_squads`. **Campaign change log:** every successful inline edit (budget/bid/status) in `PerformanceTable` and `DrilldownModal` calls `addChangeEntry()` from `src/lib/campaign-changelog.ts` — persisted to `localStorage` + KV (`br_campaign_changelog`). The **Last Change** column (on by default) reads `getEntriesForSquad(squadId)[0]` and renders the most recent change inline (field label, old→new, time ago). The **History** tab in `DrilldownModal` lists all entries for that campaign newest-first. **Checkbox range selection:** shift+clicking a checkbox in `PerformanceTable` selects/deselects all rows between the last clicked row and the current one — `lastCheckedIdx` ref tracks the anchor index; cleared on Select All / Clear Selection. The "Ignored (N)" toolbar button appears when any squads are hidden; clicking it toggles visibility of hidden rows (shown at 40% opacity with an eye icon to restore). Hidden campaigns are excluded from the `filtered` useMemo; `showHidden` state bypasses that exclusion when toggled on. **CSV download:** exports all aggregated rows with all columns regardless of visibility. Attribution: Visymo JOIN key: `snapchat_ad_squad_stats.ad_squad_id = visymo_report.custom_channel_name`. Predicto JOIN: two-path `LATERAL` JOIN — (1) **direct**: `fpc.ad_squad_snap_id = s.ad_squad_id`, written at campaign submission time via `PATCH /api/feed-providers/channels/link-squad`; (2) **name fallback**: `s.ad_squad_name ILIKE '%' || REPLACE(REPLACE(REPLACE(channel_id, '!', '!!'), '%', '!%'), '_', '!_') || '%' ESCAPE '!'` for campaigns created before the link existed — `!`, `%` and `_` in `channel_id` are escaped to prevent ILIKE wildcard injection, with an explicit `ESCAPE '!'` clause. **Both arms are additionally scoped `WHERE google_user_id = ${userId}`** — see docs/security.md. The UNION ALL is wrapped in a subquery with a `_p` priority column (`0` for direct, `1` for name fallback); `ORDER BY _p LIMIT 1` ensures the direct match always wins when both arms fire. **Critical:** match the full `channel_id` including the `+ch32` suffix (e.g. `ch57451+ch32`) — NOT just the Predicto prefix — to avoid false positives where shorter IDs (e.g. `ch5745`) are substrings of longer ones (`ch57452`). `SPLIT_PART(fpc.channel_id, '+', 1)` then extracts the bare `custom_channel_id` for the `predicto_report` JOIN. Revenue from both sources merges into `revenue_usd` — Visymo earnings are EUR→USD; Predicto revenue is already USD. Campaigns are mutually exclusive per provider. **ROI heatmap:** colored pill badges on all four ROI columns (ROI, -1D, -2D, -3D) — green ≥ 120%, orange 105–119%, red ≤ 105%, gray dash when null. **Combined/drilldown query:** Visymo pre-aggregated by `(custom_channel_name, record_date)` in subquery; Predicto pre-aggregated by `(custom_channel_id, record_date)`. Visymo fields stored: `clicks`, `earnings_eur`, `page_views`, `ad_requests`, `individual_ad_impressions`, `matched_ad_requests`, `funnel_clicks`, `funnel_impressions`, `funnel_requests`, `domain_name`. Predicto fields stored: `revenue_usd`, `clicks`, `funnel_clicks`, `funnel_impressions`, `funnel_requests`, `requests`, `impressions`. Combined query derives two extra fields: `requests` (= Visymo `ad_requests` + Predicto `requests`) and `feed_impressions` (= Visymo `individual_ad_impressions` + Predicto `impressions`). LATERAL JOIN on `feed_provider_channels` selects both `channel_id` and `feed_provider_id`; `COALESCE(fpc.feed_provider_id, '')` is exposed as `feed_provider_id` in `CombinedRow` — used by the provider filter in `PerformanceTable` for exact ID matching. **Ad squad names:** stored in `snapchat_ad_squad_stats.ad_squad_name` at sync time; `combined` reads directly from DB column — no live Snapchat API calls at query time. **Visymo sync range:** contiguous sub-ranges from `visymoDatesToFetch` so gaps don't over-fetch finalized data.

- **`swipes` vs `clicks` — the field contract every metric depends on.** In `CombinedRow`, `swipes` is the **PLATFORM** click metric (Snap swipes, or Meta link clicks) and `clicks` is **SELL-SIDE only** (Visymo + Predicto / Predicto FB). Both arms of `combined` and `drilldown` must honour this. The Meta arms previously set `swipes: 0` and added Meta's own link clicks into `clicks`, which summed two unrelated funnels into one column, left `ctr`/`cpc`/`cvr`/`fill_rate` permanently `—` for every Meta row, and diluted the portfolio CTR in `KpiSummaryBar` (Meta impressions in the denominator, no Meta clicks in the numerator). After the fix, 522 of 720 Meta rows report clicks and CTR where 0 did before. Buy-side cost metrics divide by `swipes`; sell-side revenue metrics divide by `clicks`. Never merge them.
- **All dollar↔integer conversions live in `src/lib/money.ts` (2026-08-04).** `usdToMicro`/`microToUsd` (Snapchat, ×1,000,000) and `usdToCents`/`centsToUsd` (Meta, ×100). This arithmetic was previously re-implemented in **four** places — a private `usdToMicro` in `submission-orchestrator`, an identical private `microToDollar`/`dollarToMicro` pair in **both** `PerformanceTable` **and** `DrilldownModal`, and bare `* 100` / `/ 100` in `PresetForm`, the presets page, `sync-logic` and both reporting routes. That is the same one-concept-many-paths shape as the ROAS bug, and the same two files that had already drifted on metric formulas (see `metrics.ts` below) had drifted here too. A wrong factor does not throw — it silently multiplies or divides real spend by 100 or 1,000,000. All 11 call sites now import from `money.ts`; the conversion itself is unchanged (verified arithmetically identical, `tsc --noEmit` and production build clean).
- **All derived metrics live in `src/lib/reporting/metrics.ts`.** `deriveMetrics()` is the single definition of cpm/cpc/ctr/cvr/rpc/rpr/fill_rate/profit/snap_cost_per_result, imported by both `PerformanceTable` and `DrilldownModal` (which maps `snap_cost_per_result` to its local key `cpr`). They previously computed these independently and disagreed — most visibly CPC, where the table used spend/swipes and the drilldown used spend/clicks, so one ad set showed two different CPCs. `rpc` is gated on `funnel_clicks >= 10`; `rpr` deliberately is **not**, because gating revenue-per-RESULT on a CLICK threshold dashed exactly the squads converting best. `NO_BID_TARGET_STRATEGIES` also lives here so both the table and the modal refuse a bid editor for `AUTO_BID` / `LOWEST_COST_WITHOUT_CAP`.
- **`DrilldownModal` has no bid editor for `LOWEST_COST_WITH_MIN_ROAS`.** Those ad sets carry their target in `bid_constraints.roas_average_floor` and have `bid_micro = 0`, so a plain bid editor rendered "Bid: $0.00" and would have sent `bid_amount` to an ad set that ignores it. The panel shows `ROAS: <n>%` **read-only** and defers editing to the main table's dedicated ROAS editor. The label is formatted in `PerformanceTable` and passed down as `roasLabel` — the provider's `roasDisplayDivisor` lives there, and duplicating the divisor round-trip in the modal is how the two drift apart. Note `NO_BID_TARGET_STRATEGIES` alone is **not** sufficient here: it covers `AUTO_BID`/`LOWEST_COST_WITHOUT_CAP`, and the ROAS strategy needs its own branch checked first, exactly as the table does.
- **`DrilldownModal` edits must branch on `platform`.** It receives the prop and its three save handlers (status, budget, bid) each pick `/api/meta/adsets` or `/api/snapchat/adsquads` from it. They previously all hardcoded the Snapchat route, so editing a Meta ad set sent a Meta id to Snapchat — values displayed correctly and only Save failed. Any new editor added here needs the same branch.
- **`roasDisplayDivisor` is NOT display-only, and the ROAS editor must not save an untouched draft.** The read path divides (`/100/divisor`) and `saveRoas` multiplies back (`Math.round(pct * divisor * 100)`), so a cell reading 90% at divisor 100 writes `900000` to Meta. The editor saves `onBlur`, so it needs both the `roasDraftInitial` no-op guard and full sub-percent precision in the display value; rounding to a whole percent turned a stored `9050` into `9100` on a bare click-away. Verified 0 of 109 live ROAS ad sets were affected at divisor 1, so this was latent — do not let it regress.
- **TWO conversion-value scales genuinely coexist, and `roasDisplayDivisor` is correctly compensating — DO NOT "normalise" the floors (measured 2026-08-03).** Predicto's pixel `840455538279291` reports **~$37 per conversion** where the other three pixels report **~$0.09–$0.24** for the same event type, ~300x apart; the user confirms that pixel inflates its reported values. So `900000` (Predicto) and `9000` (everyone else) are both *about break-even*, each on its own scale, and every bucket's achieved ROAS sits just above its own floor — the floors are calibrated and binding.
  - Earlier comments in `roas-floor.ts`, `PerformanceTable.tsx` and this file all advised "correct the stored floors at the source and set the divisor back to 1". **That was wrong** — it assumed a single true scale existed. Acting on it would have taken **79 live ad sets returning $264,643 on $2,255 of spend** from a binding ~90x floor to no effective floor. It only becomes safe if Predicto's pixel is fixed upstream, and then the floors and the divisor must move together in one change.
  - **The real bug, fixed 2026-08-03:** preset `roasFloor` was sent with **no divisor applied**, so a preset was implicitly bound to one provider's scale. `toRoasAverageFloorForProvider()` in `src/lib/roas-floor.ts` now multiplies by the target provider's divisor, so one preset is correct on every provider. Launching the `0.9` preset at Predicto previously wrote `9000` against inflated values — no real floor — which affected **9 ad sets in account PR1** (7 ACTIVE `WW | Phone Packages SMBs …| 2707 | V73/V74/V84`, plus 2 PAUSED `ww | Application security English | 2207 | V19/V22`).
    - **Their floors were deliberately left uncorrected — decision made 2026-08-03, do not re-propose it.** 8 of the 9 have spent **$0.00**; only the already-paused `V22` ever spent ($38.85 at ~0.41x real ROAS, ~$23 lost, over and done). So there is no accumulated loss to recover, only the forward risk that the 7 ACTIVE ones could start delivering with no effective floor. Note for anyone revisiting: the correct value would be `900000`, and that is *proven* on this exact traffic — the working ad sets at `900000` include `WW | Phone Packages SMBs (nc1) | 2707`/`2807`, same offers and same pixel.
  - **`normalizePresetRoasFloor()` is a legacy shim, not a plausibility check.** Presets hand-scaled for Predicto (value >= 10, e.g. the second "WW" preset holding `90`) are divided by 100 before the divisor is applied — without it, adding the multiplication would send that preset to `90,000,000`. 100 is the only divisor any provider uses and real floors are 0.45–1.17, so the threshold cannot catch a legitimate value. **Delete the shim once no stored preset holds a value above 10**; the two "WW" presets exist only because hand-scaling used to be required.
  - A preset's `roasFloor` is now a **TRUE ratio** (`0.9` = break even) and provider-independent. Verified all eight preset/provider combinations: `0.9` and `90` both yield `900000` at Predicto and `9000` at Vizymo.
- **Meta Insights amounts are in the AD ACCOUNT's currency, not USD.** `meta_ad_set_stats.currency` records it per row (`getAdAccountCurrency()` at sync time, defaulting to `'USD'`), and both read routes resolve every distinct rate **before** their synchronous row loop via `getRateToUsd()` — awaiting per row would serialise one fetch per stat row. Conversion happens on **read**, deliberately, so history stays reinterpretable rather than having a rate baked in. `src/lib/fx-rate.ts` handles any currency (`getEurToUsd` delegates to it) and never returns 0/undefined/NaN — a bad rate would make every ROI infinite or NaN. Currently every syncing account is USD so the rate is 1, but 2 of 33 stored accounts are ILS.
- **Attribution LATERAL joins: filter `traffic_source` CASE-INSENSITIVELY and always break ties.** The four arms across `combined` and `drilldown` filter `LOWER(traffic_source) = 'snap'` / `IN ('meta','facebook')`. **A literal `= 'Snap'` is a data-loss bug**: the table holds 8 rows with lowercase `'snap'` alongside 327 `'Snap'`, and all 8 are squad-linked, so a case-sensitive filter silently drops their revenue. `ORDER BY _p, channel_id, feed_provider_id` — the unique constraint permits one `channel_id` under several `feed_provider_id`s, and an unordered `LIMIT 1` let Postgres return a different provider between runs, which changes summary grouping, the provider filter, and which `roasDisplayDivisor` applies to an editable cell. Verified across 400 real squads: 0 change in resolved channel/provider.
